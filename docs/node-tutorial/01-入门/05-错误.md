# 错误

示例：`examples/A/05-errors.mjs`

`throw` 沿调用栈向上，直到 `try/catch`。没人接住就是未捕获异常，进程默认非 0 退出。空的 `catch` 会把失败伪装成成功。

用 `error.code` 或自定义错误的 `code` 做分支，不要比较 `message` 里的英文句子。Node 的文件错误常见 `ENOENT`、`EACCES`。中止读取是 `ABORT_ERR`。

`new Error(message, { cause })` 保留原因链。日志要打出 `cause`，否则只剩最外层的一句。`error.stack` 含服务器路径，可以进服务端日志，不要放进 HTTP 响应。

```javascript
class AppError extends Error {
  constructor(code, message, options) {
    super(message, options);
    this.name = 'AppError';
    this.code = code;
  }
}
```

示例用它拒绝非法端口。跨 Worker 或 `vm` 时，两边的 `Error` 构造函数不是同一个函数，`instanceof` 可能失败，这时认 `code`。

`try/catch` 能接住同步 `throw` 和 `await` 到的拒绝。它接不住已经离开当前栈的回调，除非回调自己捕获。浮空的 Promise 若拒绝，在 Node 22 上默认让进程退出，见[拒绝与取消](../03-运行时/13-拒绝与取消.md)。


## 是什么

`throw` 沿当前调用栈往上找 `catch`。栈已经清空之后才发生的失败，原来的 `try` 接不住。Promise 的拒绝是另一条通道：没人 `await` 或 `catch`，在 Node 15 之后默认让进程以非 0 退出。

## 为什么空的 catch 比崩溃更糟

空的 `catch` 把失败变成成功，后面的代码会拿着半初始化的状态继续写数据库。进程退出至少会让监督进程重启，并且日志里有堆栈。生产里要记日志、设置退出码，而不是吞掉。

## 错误上要带什么

用 `error.code` 或自己的 `code` 做分支。`message` 是给人读的句子，会随版本改。Node 的文件错误常见 `ENOENT`、`EACCES`、`EEXIST`。中止是 `ABORT_ERR`。

`new Error(message, { cause })` 把原因链留下来。日志要打印 `cause`，否则只剩最外层一句「请求失败」。`stack` 含服务器路径，可以进服务端日志，不要放进 HTTP 正文。

跨 Worker、`vm` 或不同上下文时，两边的 `Error` 构造函数不是同一个函数，`instanceof` 会失败。认 `code` 和 `name`。

## 同步和异步各接一次

```javascript
try {
  await readFile(path, { signal });
} catch (error) {
  if (error.code === 'ENOENT') return null;
  if (error.code === 'ABORT_ERR') return null;
  throw error;
}
```

`setTimeout` 回调里的 `throw` 不在当初那个 `try` 里。回调自己捕获，或把回调包成 Promise 再 `await`。

## 本章问答

### 1. 为什么包了 try/catch 还是抓不到定时器里的 throw？

**考点：** 调用栈和事件循环是两段时间。

**回答：** `setTimeout(fn, 100)` 只是登记。同步栈马上结束，`try` 已经退出。100ms 后 libuv 用一条新的栈调用 `fn`。要在 `fn` 里面捕获，或者让 `fn` 返回 Promise 并由调用方 `await`。见[拒绝与取消](../03-运行时/13-拒绝与取消.md)。

**易错：** 在定时器外面再包一层 `try`，以为异步错误会回来。

### 2. 未处理的拒绝在现在的 Node 里会怎样？

**考点：** Node 15 之后的默认值。

**回答：** 22.23.4 上进程非 0 退出。Node 14 及更早只打警告、进程继续跑。注册了 `unhandledRejection` 之后，默认退出不再发生，空监听器会把失败藏起来。需要监听时：记日志，然后 `process.exitCode = 1`。

### 3. 为什么不要用 instanceof 做唯一判断？

**考点：** 错误对象跨上下文。

**回答：** `instanceof AppError` 要求 `error` 的原型链上有这个进程里的那个构造函数。从另一端结构化克隆过来、或从子进程的 stderr 解析出来的对象没有这个原型。稳定的契约是字符串 `code`。

## 事故复盘

定时器回调里 `throw`，外层 `try` 接不住，进程退出，监督进程重启，重启后又触发同一个定时任务。修法是回调内部捕获，或把任务包成 Promise 并 `await`。见[拒绝与取消](../03-运行时/13-拒绝与取消.md)。

空的 `catch` 吞掉了数据库唯一约束错误，接口返回 200，用户看到成功，表里没有行。`catch` 里至少要按 `code` 分支：可恢复的返回明确结果，其余继续抛。

跨 Worker 用 `instanceof AppError` 判断失败，永远是 false，于是全部走进「未知错误」并重试。契约改成 `error.code`。

### 再答一题

**题目：** `cause` 什么时候必须保留？

**回答：** 你把底层错误换成自己的 `AppError` 时。否则日志只剩「保存失败」，看不到 `ENOENT` 或超时。`new Error(msg, { cause })` 把原因链留下。响应正文仍只给调用方的 `code`，不给 `stack`。
