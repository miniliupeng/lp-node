# 原子替换文件

示例：`examples/B/03-atomic-write.mjs`

直接 `writeFile(target, data)` 中途崩溃，目标文件可能只写了一半。同一目录里先写临时文件，再 `rename`：

```javascript
const tmp = `${file}.${process.pid}.tmp`;
await writeFile(tmp, data);
await rename(tmp, file);
```

在同一文件系统上，`rename` 替换已有文件是原子的。读者要么看到旧内容，要么看到新内容。临时文件必须和目标在同一目录，跨设备的 `rename` 会失败。

示例断言替换后的内容，并在 `finally` 里删掉目录。这只保证替换那一步。多个进程同时写同一个目标仍会互相覆盖，需要文件锁或单一写入者。

配置和缓存快照适合这个模式。数据库文件不要自己用 `rename` 拼一套事务。


## 是什么

在同一文件系统上，`rename` 替换已有文件对读者是原子的：要么看到旧内容，要么看到新内容，不会看到写到一半的新内容。做法是先把字节写到同一目录的临时文件，再 `rename` 到目标名。

## 它不保证什么

临时文件和目标不在同一文件系统时，`rename` 失败，常见代码 `EXDEV`。多个进程同时写同一个目标，后一次 `rename` 会盖住前一次，这不是锁。数据库文件有自己的日志和锁，不要用 `rename` 拼事务。

写临时文件时进程崩溃，目标仍是旧内容，临时文件可能留下。启动时可以清掉同一目录里属于自己的 `.tmp`。示例在 `finally` 里删目录。

`fs.writeFile` 直接写目标，崩溃或断电时读者可能看到半截 JSON。配置和缓存快照适合「写临时文件再替换」。需要持久化的业务数据用数据库。

## 本章问答

### 1. 为什么临时文件必须和目标同一目录？

**考点：** `rename` 不能跨设备。

**回答：** 同一目录几乎总是同一文件系统，`rename` 只改目录项。放到 `/tmp` 再挪到数据盘，经常得到 `EXDEV`。那时若退回复制，复制过程又不是原子的。

### 2. 这能不能代替文件锁？

**考点：** 原子替换和互斥不是一回事。

**回答：** 不能。两个进程可以同时写好各自的临时文件，然后先后 `rename`，最后只留下后写的那份，前一份丢失且没有报错。单写者才用这个模式。多写者要用锁或单一写入进程。

### 3. 读者会看到空文件吗？

**考点：** 替换的可见性。

**回答：** 在 `rename` 完成的那一点，目录项从旧 inode 换成新 inode。不会把目标截成 0 再慢慢写。直接 `writeFile` 到目标才可能看到半截。

## 事故复盘

配置写到 `/tmp` 再 `rename` 到数据盘，得到 `EXDEV`。代码退回复制，复制到一半进程重启，读者看到半截 JSON。临时文件放在目标同一目录。

两个进程同时发布配置，各自 `rename`，后写的覆盖先写的，没有报错，也没有合并。这个模式只适合单写者。多写者用数据库或锁。

崩溃后留下 `*.tmp`。启动时只删除自己的前缀，不要清空整个目录。
