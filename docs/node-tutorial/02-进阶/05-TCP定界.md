# TCP 定界

示例：`examples/B/05-tcp-frame.mjs`

TCP 是字节流。一次 `write` 可能被拆开，两次 `write` 也可能粘在一次 `data` 里。应用层要自己定界。

示例用 4 字节大端长度加正文：

1. 把收到的字节追加到 `Buffer`
2. 缓冲不足 4 字节就继续等
3. 读出长度，缓冲不足 `4 + length` 就继续等
4. 切出一帧，剩下的留在缓冲里

一次 `write` 里放了两帧，读取端仍拆成两条。服务把每条正文原样写回。

长度必须有上限。示例只演示拆帧，生产里要拒绝过大的长度，否则对端可以声称 2GB 让你一直分配。

不要按「一次 data 事件等于一条消息」写协议。


## 是什么

TCP 是字节流。一次 `write` 可能拆成多次 `data`，多次 `write` 也可能粘成一次 `data`。应用层要自己定界。示例用 4 字节大端长度加正文。一次 `write` 里放两帧，读取端仍拆成两条，再原样写回。

## 长度必须有上限

先读 4 字节得到长度。缓冲不足就继续等。如果信任对端声称的长度，它可以报一个巨大数字，让你按这个数字分配。示例只演示拆帧。生产里长度超过上限就断开连接，并限制缓冲总量。

不要用「读到换行」处理二进制，换行可能出现在正文里。文本协议才用分隔符，并且仍然要限制单行长度。

半个帧留在缓冲里，和下一次 `data` 拼起来。连接关闭时如果缓冲里还有半帧，这是协议错误，丢掉并记日志。

## 本章问答

### 1. 为什么一次 data 不等于一条消息？

**考点：** 字节流。

**回答：** 内核按窗口和拥塞切分，不按你的 `write` 切分。示例故意把两帧放进同一次 `write`，读取端仍得到两条。按事件次数解析会把两帧当成一帧，或把一帧的后半当成下一条的开头。

### 2. 长度字段有什么风险？

**考点：** 分配上限。

**回答：** 4 字节能表示很大的数。未设上限就会按攻击者的数字分配。超过上限应断开，而不是继续等。正文本身也要计入连接上的总缓冲。

### 3. 大端是什么意思？

**考点：** 字节序。

**回答：** 高位字节在前。`readUInt32BE` 和写入时的 `writeUInt32BE` 必须成对。一端大端、一端小端，长度会错成另一个数量级，随后的拆帧全部错位。

## 事故复盘

按每次 `data` 事件解析一条 JSON。对端把两条小消息粘在一次发送里，`JSON.parse` 失败，连接被关掉。长度前缀或分隔符要跨多次 `data` 缓冲。示例把两帧放进同一次 `write`，读取端仍得到两条。

长度字段不设上限。对端声称需要 2GB，进程开始分配，机器变慢。超过上限就断开，并限制每个连接的缓冲总量。

一端用大端写长度，另一端用小端读。长度变成另一个数量级，随后所有帧错位。读写必须成对使用 `BE` 或 `LE`。
