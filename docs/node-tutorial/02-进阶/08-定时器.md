# 定时器

示例：`examples/B/08-timers.mjs`

`setTimeout(fn, ms)` 把回调放进定时器阶段，最早在 `ms` 之后。文档规定：延迟小于 1 或大于 2147483647 会被钳成 1。所以 `setTimeout(fn, 0)` 不是「马上」。

`setImmediate(fn)` 放进 check 阶段。主模块里两者谁先执行，22.23.4 上不稳定。示例只断言两件事都发生了，不断言先后。I/O 回调里的稳定顺序见[定时与读写顺序](../03-运行时/04-定时与读写顺序.md)。

`setInterval` 会按间隔反复排队。回调本身花的时间不算在间隔里，慢回调会堆积。

`timer.unref()` 让这个定时器不阻止进程退出。示例建了一个 60 秒的定时器并 `unref`，脚本仍能结束。服务器的心跳可以用它，业务超时不要 `unref`，否则进程退出时它根本不会触发。

`import { setTimeout } from 'node:timers/promises'` 后可以 `await setTimeout(10, 'ok', { signal })`。中止后拒绝，`name` 是 `AbortError`。


## 是什么

`setTimeout` 把回调放进 timers 阶段，最早在给定延迟之后。文档把小于 1 或大于 2147483647 的延迟钳成 1。所以 `setTimeout(fn, 0)` 不是「马上」，至少约 1ms，而且要等事件循环转到 timers。

`setImmediate` 在 check 阶段。主模块里两者谁先，22.23.4 上不稳定。示例只断言两件事都发生。I/O 回调里的稳定顺序见[定时与读写顺序](../03-运行时/04-定时与读写顺序.md)。

## unref 和中止

`timer.unref()` 让这个定时器不阻止进程退出。心跳可以用它。业务超时不要 `unref`，否则进程退出时它根本不会触发。示例建了一个 60 秒的定时器并 `unref`，脚本仍能结束。

`timers/promises` 的 `setTimeout(ms, value, { signal })` 可以被中止，拒绝的 `name` 是 `AbortError`。`setInterval` 的间隔不包含回调自己的执行时间。回调慢于间隔时，调用会堆积。能用递归 `setTimeout` 把下一次排在本次完成之后，就不要用短间隔的 `setInterval` 做重活。

嵌套的 `nextTick` 会把定时器饿住。`examples/C/17-nexttick-starve.cjs` 在 400 次 `nextTick` 结束前，`timeout` 和 `immediate` 都还没发生。

## 本章问答

### 1. setTimeout(fn, 0) 为什么不是下一行就执行？

**考点：** 钳制和阶段。

**回答：** 延迟被钳成至少 1ms，回调放在 timers 阶段。当前栈、nextTick 和微任务都先走完。主模块里它和 `setImmediate` 的先后不稳定，不要用一次打印当作规范。

### 2. 什么定时器该 unref？

**考点：** 进程生命周期。

**回答：** 只用于观察、丢了也不影响正确性的心跳。请求超时、锁续期不要 `unref`，进程退出时它们不会再跑，业务会停在半截状态。

### 3. 递归 nextTick 有什么后果？

**考点：** 饥饿。

**回答：** nextTick 队列不空，事件循环进不了 timers、poll 和 check。网络和定时器都停。示例把递归限制在 400 次，并断言在此之前两个宏任务都还没记录下来。无限递归会让进程看起来活着，却不再接受连接。

## 事故复盘

用 `setTimeout(fn, 0)` 保证「一定在 setImmediate 之前」。主模块里这个顺序不稳定，测试偶尔失败。需要稳定顺序时，把注册放进 I/O 回调，或不要依赖这两者的先后。

心跳定时器忘了 `unref`，测试进程不退出，CI 卡到超时。反过来，业务超时被 `unref`，进程退出时锁没有续期，另一边拿到了同一把锁。

`setInterval` 的回调比间隔还慢，调用堆积，内存上涨。重活改成做完再排下一次 `setTimeout`。
