# 服务器发送事件

示例：`examples/B/14-sse.mjs`

SSE 是服务端单向推文本。响应头是 `text/event-stream`。事件之间用空行分开。默认事件名是 `message`。以冒号开头的行是注释，常用来发心跳。

```text
event: ping
data: hello

: keepalive

data: world

```

示例解析这两段，得到 `ping` / `hello` 和默认的 `message` / `world`。

22.23.4 没有全局 `EventSource`。浏览器里有。服务端要推送给浏览器时，自己写响应流，并在客户端断开时 `res.end()` 或停止定时器。

一条 `data` 里的换行要拆成多行 `data:`。示例的解析器按空行切事件。生产实现还要处理 `id` 和 `retry`。

SSE 走普通 HTTP，代理要关掉这段响应的缓冲，否则事件会攒一批才到浏览器。


## 是什么

SSE 是服务端单向推文本。响应头是 `Content-Type: text/event-stream`，再加 `Cache-Control: no-cache`。事件之间用空行分开。默认事件名是 `message`。以冒号开头的行是注释，常用来做心跳。一条数据里的换行要拆成多行 `data:`。

22.23.4 没有全局 `EventSource`。浏览器里有，并且会用 `Last-Event-ID` 尝试重连。Node 服务端要自己写响应流。

## 和 WebSocket、和 2026 年的 MCP 不是一回事

AI 对话经常用 SSE：一次请求，服务端连续写 token。客户端断开时要停，见 `examples/D/12-sse-cancel.mjs` 和[流式生成与取消](../04-工程与系统设计/20-流式生成与取消.md)。

模型上下文协议在 2024-11-05 曾用独立的 HTTP+SSE 传输。2025-03-26 起改为 Streamable HTTP。2026-07-28 又去掉了单独的 GET 流和协议级会话。不要把「浏览器里的 SSE」和「MCP 的传输」说成同一个东西。MCP 见[模型上下文协议](../04-工程与系统设计/19-模型上下文协议.md)。

代理和压缩中间层会缓冲 `text/event-stream`。要关掉这段响应的缓冲，否则事件会攒一批才到浏览器。

## 本章问答

### 1. 为什么 AI token 常用 SSE 而不是 WebSocket？

**考点：** 方向和现有的 HTTP 设施。

**回答：** 用户发一次请求，模型单向吐字。SSE 就是带特殊正文的 HTTP 响应，能走现有的认证、网关和状态码。WebSocket 是双向升级，心跳和代理都要额外处理。需要客户端持续发二进制帧时才用 WebSocket。

### 2. Node 里能 new EventSource 吗？

**考点：** 全局对象是否存在。

**回答：** 22.23.4 不能。服务端写 `text/event-stream`。测试里用 `fetch` 读流，或像示例那样自己解析事件文本。

### 3. 客户端断开之后服务端应做什么？

**考点：** 停掉还在花钱的工作。

**回答：** 听 `req` 的 `close`，停下循环，不再调用上游模型。示例在写出少量事件后中止客户端，并断言发出的条数小于全部 token。

## 事故复盘

反向代理默认缓冲响应。用户等了 30 秒才一次性看到全部 token。对 `text/event-stream` 关掉缓冲。

服务端不听 `close`。用户已经离开，模型调用仍在计费。见 `examples/D/12-sse-cancel.mjs`。

在 Node 里 `new EventSource`。22.23.4 没有这个全局对象，启动就抛 `ReferenceError`。服务端写事件流，测试用 `fetch` 读。
