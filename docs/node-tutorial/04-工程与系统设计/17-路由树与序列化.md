

# 路由树与序列化

标准库的路由可以是一次 `pathname` 比较，见[HTTP 路由与正文](../02-进阶/06-HTTP路由与正文.md)。路由变多以后，线性扫描每条规则的代价随规则数增长。前缀树按路径上的片段往下走，代价跟路径长度相关，不跟规则总数线性增长。这是 `find-my-way` 一类实现的思路。本教程没有在这台机器上测量「快几倍」，不把倍数写进答案。

## 是什么

前缀树的节点是一段共同前缀。`/users/new` 和 `/users/:id` 共享 `/users/`，到了下一段再分支。参数段和静态段同时存在时，静态段优先，否则 `new` 会被当成 id。

序列化也有两条路。`JSON.stringify` 在运行时看对象上有哪些键、值是什么类型。若响应形状由 JSON Schema 固定，可以在启动时按 schema 生成一段只拼接这些字段的函数，省掉每次的形状探测。字段和 schema 不一致时，生成的函数可能丢掉未声明的键，这是契约，不是意外。

## Fastify 风格的钩子顺序

下面是这类框架常见的请求顺序，用来面试时把名字说全，不是本仓库示例的实现：

1. `onRequest`：还没有解析正文。适合请求 id、访问日志的开始。
2. `preParsing`：正文解析之前。
3. `preValidation`：schema 校验之前，可以改写原始输入。
4. `preHandler`：校验已经通过。适合鉴权。鉴权放在校验前会让坏请求也去查会话。
5. 处理函数。
6. `preSerialization`：对象还没变成字符串。
7. `onError`：上面任一步抛错。
8. `onResponse`：字节已经写出。适合记耗时。不要在这里再改状态码。

插件封装：子上下文能看见父级的装饰器，子级注册的路由和钩子不反向污染父级和兄弟。数据库连接这种全应用都要用的东西，要用框架提供的「跳过子上下文」包装，否则只有注册它的那个插件看得见。

## 本章问答

### 1. 线性路由和前缀树差在哪？

**考点：** 代价跟什么走。

**回答：** 线性路由按注册顺序试每条规则，规则越多越慢。前缀树按路径片段下降，静态段优先于参数段。本教程不给出未经测量的倍数。路径短、规则少时，一次 `===` 更清楚，也够用。

### 2. 按 schema 生成序列化函数得到什么，失去什么？

**考点：** 契约和灵活性。

**回答：** 得到稳定的字段集合，少做运行时形状探测。失去「对象上临时加的字段会自动出现在 JSON 里」。多出来的字段要改 schema 并重新生成，而不是只改对象。

### 3. 鉴权放在哪个钩子？

**考点：** 校验和身份的顺序。

**回答：** 放在校验通过之后的 `preHandler`。更早会让格式错误的请求也访问会话存储。`onRequest` 适合还没碰正文就能做的事，例如请求 id。

## 事故复盘

参数路由写在静态路由前面，`/users/new` 被当成 id `new`。静态段优先。路径少时用相等比较，不要为了树状结构牺牲可读性。

按 schema 生成的序列化函数丢掉了临时加上的 `debug` 字段，排错时以为服务没返回。未声明的字段不会自动出现。改契约就要改 schema。

鉴权放在正文解析之前，坏 JSON 也去查会话存储，把存储打满。身份检查放在校验通过之后。
