# 系统设计

示例：`examples/D/05-short-url.mjs`。

把需求收成能核对的行为，再谈组件。短链示例只做三件事：

1. `POST /links?url=` 接受 `http` 或 `https` 开头的地址，返回 `{ code }`。
2. 同一个 URL 再次创建，得到同一个 code。
3. `GET /{code}` 回 302，`Location` 是原地址。未知 code 回 404。

code 是进程内递增序号的 36 进制。映射在内存 `Map` 里。进程退出后链接消失，也不能在多个实例之间共享。这足够说明接口，不够当生产系统。

往生产推进一步时要单独回答：

| 问题 | 示例里的答案 | 多实例时 |
| --- | --- | --- |
| 相同 URL 是否总是同一个 code | 是，靠 `byUrl` | 需要共享存储上的唯一约束 |
| code 会不会冲突 | 单进程递增，不会 | 发号要原子，或改用随机码并重试冲突 |
| 数据会不会丢 | 会，只在内存 | 写入数据库 |
| 打开短链要不要鉴权 | 不需要 | 若地址敏感，302 前先检查权限 |
| 恶意地址 | 只检查协议前缀 | 还要限制长度，并考虑开放重定向 |

容量估算先给数量级：每天多少次创建、多少次跳转、数据保存多久。跳转通常比创建多，读路径要能缓存。缓存失效和数据库仍是事实来源。

限流、队列和退出见同目录的对应章。面试时先画请求路径，再讲失败和重复，最后才讲用什么存储。


## 是什么

先写能核对的行为，再谈组件。短链示例只做三件事：创建时只接受 `http` 或 `https`，相同 URL 得到同一个 code，打开时 302 到原地址，未知 code 404。code 是进程内递增序号的 36 进制，存在内存 `Map` 里。

## 示例保证不了什么

| 问题 | 单进程示例 | 多实例 |
| --- | --- | --- |
| 相同 URL 是否总是同一个 code | 是，靠 `byUrl` | 共享存储上的唯一约束 |
| code 会不会冲突 | 单进程递增，不会 | 发号要原子，或用随机码并重试冲突 |
| 重启后还在吗 | 不在 | 写入数据库 |
| 敏感地址 | 只检查协议 | 还要限制长度、鉴权，避免开放重定向 |

跳转通常比创建多。读路径可以缓存，数据库仍是事实来源。容量先给数量级：每天多少次创建、多少次跳转、保存多久。

## 本章问答

### 1. 为什么相同 URL 要不要映射到同一个 code，必须先问清楚？

**考点：** 需求而不是数据库。

**回答：** 示例选择了要。那就要唯一约束。如果每次创建都是新 code，存储和缓存策略都不同。没问清楚就选数据库，方案是空的。

### 2. 302 有什么安全问题？

**考点：** 开放重定向。

**回答：** 若允许任意地址，这个服务会变成跳板。示例只接受 `http:` 和 `https:`。生产还要限制长度，并决定是否只允许一份主机名单。

### 3. 内存 Map 离生产差哪几步？

**考点：** 丢失、共享、发号。

**回答：** 重启即失，多实例不共享，递增序号在多个进程里会冲突。补上持久化和原子发号之后，才谈缓存。缓存不能当唯一事实来源。

## 事故复盘

短链用内存 `Map` 上了两台机器。同一 URL 得到两个 code，重启后全部 404。多实例要共享存储和原子发号。示例只保证单进程里的幂等和 302。

允许任意 `Location`。服务被当成开放跳转。只接受 `http:` 和 `https:`，并限制长度和主机名单。

先选了数据库，没问相同 URL 是否必须对应同一个 code。这个选择决定有没有唯一约束。先写行为，再写存储。
