# 模型上下文协议

示例：`examples/D/11-mcp.mjs`。它只演示 JSON-RPC 的工具列举和调用，不是一份完整的协议实现。

## 是什么

模型上下文协议（MCP）用 JSON-RPC 2.0 让客户端发现并调用服务器提供的工具、资源和提示词。工具是模型可以调用的函数。资源是只读上下文。提示词是预先写好的模板。

规范在变，讲的时候要带修订日期。

| 修订 | 远程传输里和本章有关的事实 |
| --- | --- |
| 2024-11-05 | 独立的 HTTP + SSE |
| 2025-03-26 至 2025-11-25 | Streamable HTTP。可以有会话头、GET 打开的 SSE、用 `Last-Event-ID` 续传 |
| 2026-07-28 | 仍叫 Streamable HTTP，但是 POST-only。去掉协议级会话和 GET 流。每个 JSON-RPC 请求单独 POST。响应可以是一个 JSON 对象，或只属于这一次请求的 SSE。客户端在头里和 `_meta` 里带协议版本。新增 `server/discover`。`initialize` 握手不再是这版的必须步骤 |

本地进程之间仍用标准输入输出。远程用上面的 HTTP。不要把浏览器里的 `EventSource` 教程当成 2026-07-28 的服务器写法。

## 示例做了什么

`tools/list` 返回 `query_user`，`resultType` 是 `complete`。`tools/call` 在 `id` 为 `u1` 时返回文本 `ada`。找不到用户时，JSON-RPC 本身成功，结果里 `isError: true`。这是工具失败，不是「方法不存在」。未知方法返回错误码 `-32601`。没有 `id` 的通知不产生响应。

示例没有实现 `server/discover`、`_meta` 里的协议版本、订阅和多轮 `input_required`。这些写在这里，避免把教学子集说成整个规范。

## 本章问答

### 1. 2026-07-28 的远程传输还是单独开一条 GET SSE 吗？

**考点：** 规范修订，而不是框架口号。

**回答：** 不是。这一版每个请求是一次 POST。服务器可以用一个 JSON 对象回答，或用这一次响应上的 SSE 把通知和最终结果写完。2025-03-26 到 2025-11-25 才有独立 GET 流和会话头。更早的 2024-11-05 是 HTTP+SSE。实现要声明自己支持哪一版。

### 2. 工具执行失败应该用 JSON-RPC error 吗？

**考点：** 协议错误和业务错误。

**回答：** 方法名未知用 `-32601`。参数或工具名不合法可以用 `-32602`。工具自己没找到用户时，示例返回正常结果且 `isError: true`，让客户端把这段文本交回模型。不要把所有失败都变成同一种错误码。

### 3. 为什么示例不叫完整 MCP 服务器？

**考点：** 子集。

**回答：** 没有传输层、没有协议版本协商、没有资源和提示词、没有 `server/discover`。它只把工具调用的 JSON 形状跑通。生产实现要按所声明的修订日期补齐，并限制工具能碰到的文件和网络。

## 事故复盘

按 2024 年的文章做了一个长连接 SSE 服务器，客户端按 2026-07-28 只发 POST。两边都说自己实现了 MCP，工具调用对不上。声明协议修订日期。2026-07-28 没有协议级会话，也没有单独的 GET 流。

工具没找到用户时返回 JSON-RPC `-32601`。客户端以为方法不存在，不再重试参数。方法未知才用 `-32601`。工具失败用结果里的 `isError`。示例把这两种分开了。

示例被当成生产服务器直接暴露。它没有版本协商、资源和权限边界。教学子集不能监听公网。
