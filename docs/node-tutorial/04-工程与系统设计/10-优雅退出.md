# 优雅退出

示例：`examples/D/04-graceful.mjs`。

`server.close()` 拒绝新连接，已经接受的请求继续跑完。示例里：

1. `/slow` 要 80ms 才写完正文。
2. 10ms 后调用 `close`。
3. 新的 `fetch` 失败。
4. 原来的慢请求仍然返回 `slow`。

收到 `SIGTERM` 时按这个顺序：

1. 停止接收新请求（`server.close`）。
2. 停止拉取新的队列任务。
3. 等待正在处理的请求，但设置一个上限。
4. 关闭数据库。
5. 进程退出。超时仍不结束，就记录之后再退出，避免部署被拖住。

`process.exit()` 会立刻结束，慢请求会被掐断。示例没有调用它。

Kubernetes 或进程管理器会先发 `SIGTERM`，隔一段时间再 `SIGKILL`。收尾时间要短于这个宽限。

keep-alive 连接会让 `close` 的回调很晚才执行。示例的探测请求不用 keep-alive。生产里在关闭时结束空闲连接。


## 是什么

`server.close()` 拒绝新连接，已经接受的请求继续跑完。示例里 `/slow` 要 80ms。10ms 后 `close`。新的 `fetch` 失败。原来的慢请求仍然返回 `slow`。

## 收到 SIGTERM 的顺序

1. 停止接受新请求。
2. 停止拉取新的队列任务。
3. 等待在途请求，但有上限。
4. 关闭数据库。
5. 进程退出。到点仍不结束就记日志再退出，避免部署被拖住。

`process.exit()` 会立刻掐断慢请求。示例没有调用它。监督进程先发 `SIGTERM`，隔一段时间再 `SIGKILL`。收尾要短于这个宽限。

keep-alive 连接会让 `close` 的回调很晚才到。示例的探测不用 keep-alive。生产里在关闭时结束空闲连接。

滚动替换多个 Worker 时，一次只停一个，见[多进程](../03-运行时/10-多进程.md)。

## 本章问答

### 1. close 会取消正在跑的请求吗？

**考点：** 新连接和在途请求。

**回答：** 不会。它停止 `accept`。已接受的请求继续写完。示例用 80ms 的响应在 `close` 之后仍得到正文，同时新请求失败。

### 2. 为什么不能一开始就 process.exit？

**考点：** 半截响应。

**回答：** `exit` 不等回调。客户端看到连接断开，业务可能已经写了一半。先 `close`，再在超时之后退出。

### 3. keep-alive 为什么会拖住退出？

**考点：** 空闲连接也算打开着。

**回答：** `close` 要等现有连接结束。空闲的 keep-alive 没有请求在跑，但套接字还在。关闭时主动结束这些空闲连接，否则要等到它们自己超时。

## 事故复盘

收到 `SIGTERM` 就 `process.exit(0)`。80ms 的响应被掐断，客户端重试，写操作做了两次。先 `server.close()`，等在途请求，再退出。示例断言慢请求仍返回正文，新请求失败。

keep-alive 空闲连接让 `close` 的回调一直不到，部署超时后被 `SIGKILL`。关闭时结束空闲连接。

滚动发布一次停掉所有进程。应先有新进程接流量，再停旧的。
