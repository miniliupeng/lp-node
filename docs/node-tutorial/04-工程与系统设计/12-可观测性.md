# 可观测性

测量方法见 [性能测量](../03-运行时/11-性能测量.md)。日志见 [日志](./03-日志.md)。

上线后要能回答三个问题：服务还活着吗，慢在哪，错在哪。

- **活着**：`GET /health` 只表示进程能响应。依赖数据库的就绪检查单独做，失败时让负载均衡摘掉这个实例。
- **慢**：记录请求耗时。主线程被同步代码堵住时，`monitorEventLoopDelay` 的最大值会升高，单位是纳秒。
- **错**：未处理拒绝在 Node 22 默认让进程非 0 退出。捕获之后要记日志并带上请求 id，不要注册空的 `unhandledRejection`。

指标至少有：请求数、按状态码分类的错误数、延迟、事件循环延迟、进程内存。`process.memoryUsage().arrayBuffers` 能看到 Buffer，只看 `heapUsed` 会漏掉。

多进程时每个进程各打各的日志，用请求 id 把同一次请求串起来。Worker 和子进程不会继承 `AsyncLocalStorage`，id 要放进消息里。


## 是什么

上线后要能回答三个问题：进程还活着吗，慢在哪，错在哪。

活着：`GET /health` 只表示进程能写响应。依赖数据库的检查单独做，失败时让负载均衡摘掉这个实例。不要让每一次健康检查都打满数据库。

慢：分开量事件循环延迟和下游耗时。`monitorEventLoopDelay` 的单位是纳秒，见[性能测量](../03-运行时/11-性能测量.md)。

错：未处理拒绝在 Node 22 默认让进程退出。捕获之后记日志并带上请求 id。不要注册空的 `unhandledRejection`。

## 最少要有的数字

请求数、按状态码分的错误数、延迟、事件循环延迟、`rss` 和 `arrayBuffers`。只看 `heapUsed` 会漏掉 Buffer。多进程各自打日志，用请求 id 把同一次调用串起来。Worker 不继承异步存储，id 放进消息。

## 本章问答

### 1. 健康检查为什么不要做重查询？

**考点：** 检查本身变成负载。

**回答：** 每个副本每几秒一次。重查询会在故障时把数据库打得更满。存活只证明进程能响应。就绪才检查依赖，并且要有超时。

### 2. 怎样区分事件循环慢和数据库慢？

**考点：** 两段时间。

**回答：** 事件循环延迟高、而数据库调用的等待时间短，主线程上有同步代码。数据库等待长、延迟正常，慢在下游。两段绑在一个总计时里就分不出来。

### 3. 空的 unhandledRejection 有什么问题？

**考点：** 它关掉默认退出。

**回答：** 进程继续跑，错误没有日志。状态可能已经错了。监听器里至少要记下原因。不能恢复就非 0 退出。

## 事故复盘

健康检查每次做重查询。数据库慢的时候，检查自己把连接池打满。存活只证明进程能响应。就绪才碰依赖，并且要有超时。

一个总计时同时包含 SQL 和 JSON 序列化。优化了索引，延迟不变，因为慢在主线程。事件循环延迟和下游耗时分开记。

空的 `unhandledRejection` 让进程活着，错误没有指标。报警要建立在真的记下了原因的前提下。
