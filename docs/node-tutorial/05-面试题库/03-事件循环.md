# 事件循环

正文：[事件循环](../03-运行时/02-事件循环.md)、[任务队列](../03-运行时/03-任务队列.md)、[定时与读写顺序](../03-运行时/04-定时与读写顺序.md)、[拒绝与取消](../03-运行时/13-拒绝与取消.md)。

## 1

**题目：** 说出和日常代码有关的事件循环阶段。`nextTick` 是阶段吗？

**难度：** 基础

**考察点：** 阶段名称，以及不要把队列说成阶段。

**参考答案：** timers、pending callbacks、idle/prepare、poll、check（`setImmediate`）、close callbacks。`process.nextTick` 不是阶段。`queueMicrotask` 和 Promise 回调也不是。它们在 JavaScript 回调结束之后被排空。

**易错点：** 把 `nextTick` 画成 timers 和 poll 之间的一个正式阶段。

**追问：** `MessageChannel` 的 `message` 是微任务吗？不是。CJS 顶层示例的顺序是 nextTick、微任务、message、immediate。

## 2

**题目：** 同一段「先 nextTick、再微任务」的注册，CJS 顶层和 ESM 入口顺序为什么不同？

**难度：** 深入

**考察点：** 入口本身在不在微任务检查点里。

**参考答案：** 一次调用结束后，Node 先排空 nextTick（包括嵌套的 nextTick），再进入微任务检查点。微任务里新排的 nextTick 留到这次检查点之后。CJS 顶层因此是 `nt1 → nt2 → mt1 → p1 → mt-from-nt → mt2 → nt-from-mt`。ESM 入口的求值发生在微任务检查点里，同一段注册得到 `mt1 → p1 → mt2 → nt1 → nt-from-mt → nt2 → mt-from-nt`。已经在 Promise 回调里时，新微任务先于新的 nextTick：`microtask → promise → nextTick`。

**易错点：** 背一条「永远 nextTick 优先」。ESM 入口和 Promise 回调里都不成立。

**追问：** CJS 里 `async` 函数的同步部分、`await` 之后的恢复，和 nextTick 谁先？同步部分先执行，然后 nextTick，然后 `await` 的恢复和其他微任务。示例外层顺序是 `async-start → nextTick → after-await → promise → microtask`。

## 3

**题目：** 主模块里 `setTimeout(fn, 0)` 和 `setImmediate` 谁先执行？I/O 回调里呢？

**难度：** 进阶

**考察点：** 哪些顺序稳定，哪些不稳定。

**参考答案：** 主模块里不稳定，示例不断言先后。`setTimeout` 的延迟小于 1 或大于 2147483647 会被钳成 1。在 `readFile` 回调里依次注册时，22.23.4 上稳定为 nextTick、微任务、`setImmediate`、`setTimeout`。`setImmediate` 在随后的 check 阶段，零延迟定时器要等后面的 timers。

**易错点：** 用一次运行的打印结果证明「`setTimeout(0)` 永远更早」。

## 4

**题目：** 没有 `catch` 的 `Promise.reject` 会怎样？空的 `unhandledRejection` 监听器呢？

**难度：** 进阶

**考察点：** Node 15 之后的默认退出。

**参考答案：** 22.23.4 上进程非 0 退出，stderr 里有错误信息。注册 `unhandledRejection` 之后，这个默认退出不再发生，哪怕监听器是空的。空监听器会把失败藏起来。需要监听时，记录错误并设置非 0 退出码。

**易错点：** 说「Node 会在 `unhandledRejection` 里打印然后继续跑」。默认是退出。加上空监听器之后才会继续。

**追问：** 已经 abort 的 `readFile` 错误码是什么？`ABORT_ERR`，名称 `AbortError`。


## 5

**题目：** 递归 `process.nextTick` 会造成什么？怎样用实验说明定时器被挡住了？

**难度：** 深入

**考察点：** 饥饿，而不是再背一遍阶段名。

**参考答案：** nextTick 队列不空时，事件循环进不了 timers 和 check。`examples/C/17-nexttick-starve.cjs` 在 400 次 nextTick 结束的那一次里断言 `timeout` 和 `immediate` 都还没发生，队列清空后它们才会出现。无限递归会让进程不再读网络，看起来却没崩溃。

**易错点：** 把 `nextTick` 当成「更快的 setTimeout」。它不在定时器阶段，也不能用它做循环。

**追问：** ESM 入口为什么不能背「nextTick 绝对优先」？模块求值在微任务检查点里，同一段注册会先跑微任务。两组顺序都有断言。

## 事故复盘

六阶段背得很熟，但说不清 ESM 和 CJS 的差别，也说不出递归 nextTick 会饿死 I/O。阶段名是 1 分。能指出 `examples/C/17-nexttick-starve.cjs` 在队列清空前看不到定时器，才到 3 分。
