# D14 系统设计

可运行的核心：短链 [`D/05-short-url.mjs`](../../../examples/node-tutorial/D/05-short-url.mjs)、限流 D08、队列 D09。下面每题都按同一顺序：目标、接口、数据、热点、失败。

## 短链

**目标**：把长 URL 换成短码，访问短码时 302 到原地址。本机示例用内存 `Map`，短码是递增的 36 进制数，同一 URL 返回同一短码。

**接口**：`POST /links?url=` 校验协议前缀 `http://` 或 `https://`，返回 201 `{ code }`。`GET /{code}` 找到就 302，找不到就 404。

**生产还要加的**：

- 短码不可预测，避免被人遍历。递增 id 会暴露数量。可以用随机字节再检查冲突
- 持久化。示例进程退出就丢
- 读多写少：短码到 URL 的缓存，缓存失效跟着重定向数据走
- 滥用：禁止内网地址、限制创建速率（D08）、记录创建者
- 302 适合目标还会改的场景。301 会被客户端长期记住

示例断言了重复创建得到同一 code，以及 `redirect: 'manual'` 时状态码 302、`location` 正确。

## 上传

**目标**：接收大文件，不把整个文件放进内存。

**做法**：请求体用流，`pipeline` 到临时文件，写完再 `rename` 到正式位置（B03）。大小在流里累计，超过上限就销毁请求并删除临时文件。校验魔数或内容类型在落盘之后、对外提供之前。路径用 D11 的根目录检查。

多个实例时，正式位置在对象存储，不在某一台机器的磁盘。

## 聊天或推送

**目标**：把消息送给在线连接。

**单进程**：`Map<roomId, Set<socket>>`。连接断开时从 Set 移除。

**多进程**：连接在 A 机器，消息从 B 机器进来。需要一台总线（发布订阅）。每台机器只向自己持有的套接字写。不要假设 cluster 的轮询会把同一用户的两条消息分到同一进程；长连接根本不会按消息重新分配。

心跳：服务器发 ping，超时未收到 pong 就关掉，避免半开连接占着 `Map`。

## 任务系统

**目标**：用户提交一个耗时工作，接口马上返回工作 id，完成后能查询。

**做法**：接口把消息放进队列（D09）并写一行“已接受”。工作者领取、执行、把结果写回、再确认。接口和工作者是不同的进程，可以分别扩容。

用户查询读数据库，不读工作者内存。至少一次投递要求执行是幂等的。

## 容量

先写数字：每秒请求、正文大小、保留天数、可接受的 p99。由此得到连接数、存储和进程数。Node 进程的并发连接可以很多，CPU 重的部分单独算。没有数字的设计题，先把数字问出来再画框。

## 自测

1. 为什么短链示例的递增码不能直接上生产？可以被遍历，也没有持久化。
2. 聊天服务加第二台机器时，第一件事是什么？让两台机器能把消息交给持有该连接的那一台。
3. 上传为什么用临时文件再 rename？避免读者看到半个文件。
