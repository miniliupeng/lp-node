# D09 任务队列

对应示例：[`examples/node-tutorial/D/03-queue.mjs`](../../../examples/node-tutorial/D/03-queue.mjs)

## 至少一次

示例是单个进程里的数组：

- `push` 放入载荷，返回 id
- `pull(now, visibilityMs)` 取一条 `visibleAt <= now` 的任务，并把 `visibleAt` 设成 `now + visibilityMs`
- 在可见性窗口内，第二次 `pull` 取不到它
- 窗口过去还没 `ack`，同一条 id 可以再次被取到
- `ack` 从数组里删除

这就是“至少一次”：工作者崩溃、没来得及确认时，任务会再次出现。工作者必须能安全地执行两次。发送邮件前先记下“这封已经发过”的键，或者让下游按幂等键去重。

“最多一次”是崩溃就丢。“恰好一次”在进程会崩、网络会重试的条件下，通常落成“至少一次 + 幂等副作用”。

## 示例没有的部分

- 多个消费者同时 `pull` 需要原子领取。内存数组只因为 JavaScript 主线程一次只跑一段代码才安全
- 失败次数达到上限后进入死信，给人检查，而不是永远重试
- 延时、优先级、延迟队列
- 持久化。进程一退出，示例里的数组就没了

这些由 Redis、数据库表或专门的队列服务提供。Node 进程是生产者和消费者，不是队列本身。

## 消费者怎么写

循环：领取 → 执行 → 确认。执行失败就不要确认，等可见性过期后重试。每次失败增加计数。重试之间用 E03 的退避，避免打爆下游。

消费者数量受下游容量限制。10 个进程同时写同一行数据库，队列本身不是瓶颈。

## 自测

1. 工作者在 `ack` 之前崩溃会怎样？可见性过期后任务再次可见。
2. 为什么处理函数必须能跑两次？因为至少一次投递。
3. 为什么不能只用进程内存当生产队列？进程退出数据就丢，也不能在多个副本之间共享。
