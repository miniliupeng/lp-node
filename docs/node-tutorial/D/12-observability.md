# D12 可观测性

测量 API 见 [C11](../C/11-performance.md) 和 [`C/11-perf.mjs`](../../../examples/node-tutorial/C/11-perf.mjs)。

## 三个问题

| 信号 | 回答 |
| --- | --- |
| 日志 | 这一次请求发生了什么，错误栈是什么 |
| 指标 | 速率、错误比例、延迟分布、事件循环延迟、池子是否用尽 |
| 追踪 | 这一次请求穿过了哪些服务，时间花在哪一段 |

三者用同一个请求号串起来。日志字段见 D03。指标是数字，可以聚合；不要把用户 ID 放进指标标签，否则标签基数会打爆存储。

## Node 进程里值得看的指标

- 每条路由的请求数、状态码、延迟直方图
- `monitorEventLoopDelay` 的 p99
- `process.memoryUsage()` 的 `rss` 和 `arrayBuffers`
- 句柄数量：活跃套接字、队列深度
- 线程池是否排队（表现是文件和 DNS 变慢，同时 CPU 未满）

延迟用直方图，不用平均值。平均值会把一次 10 秒的停顿藏在大量 5ms 的请求里。

## 追踪

跨服务时，入口生成 trace id，放进出站 HTTP 头。`AsyncLocalStorage` 在一个进程内传递它。队列消息把 trace id 放进消息体，消费者再 `run` 一次。

OpenTelemetry 是这套数据的常见导出方式。教程不内置收集器。先把请求号和延迟打到 stdout，确认字段正确，再接收集器。

`diagnostics_channel` 是 Node 内部和框架用来发诊断事件的通道。应用代码优先用明确的日志和指标，而不是订阅内部通道。

## 自测

1. 为什么延迟看分位数而不是平均数？平均数掩盖长尾。
2. 事件循环延迟高、CPU 也高，优先查什么？主线程上的同步计算或 GC。
3. 事件循环延迟高、CPU 很低，优先查什么？在等 I/O，或线程池排队。
