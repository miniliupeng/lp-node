# D13 部署

## 进程模型

一个服务进程应当可以在任何时候被杀掉并用新进程替换（D10）。状态不放在进程里。

同一台虚拟机上，可以用 cluster 占用多个核（C10），也可以启动多个容器。不要同时让 cluster、pm2 和 Kubernetes 都去重启它。选一个负责拉起。

容器里的 Node 进程作为 PID 1 时，要能把 `SIGTERM` 传给自己的处理函数。有的镜像用 shell 当 PID 1，信号停在 shell 上，`server.close` 不会运行。直接用 `node` 当入口，或使用会转发信号的初始化程序。

## 反向代理

代理负责 TLS、请求体大小的第一道限制、空闲超时。Node 只听内网地址。`X-Forwarded-For` 只有在你信任的代理后面才能用来识别客户端 IP，否则客户端可以伪造这个头。

代理的超时要大于应用的优雅退出时间，小于客户端愿意等的时间。三条超时互相矛盾时，写下来再选。

## 资源

- 内存上限略高于 `--max-old-space-size`，让 V8 先抛出可记录的错误，而不是被系统直接杀掉却没有堆栈。两者的差距留给 Buffer 和线程栈
- CPU 限制会拉长事件循环延迟。限制是为了隔离，不是为了让 Node “更省”
- 只读根文件系统能减少进程写到意外路径的机会。临时文件指向挂载的 tmp

## 健康检查

存活检查：进程还能回答 `GET /health`，事件循环没有卡死。就绪检查：数据库连接可用，才接收流量。

不要在存活检查里查询一个已经超时的下游，否则下游抖动会导致进程被反复杀掉。存活和就绪分开。

## 发布

滚动替换：新进程就绪后再把流量转过去，旧进程收到 `SIGTERM`。数据库迁移先做向后兼容的那一步（加列、双写），再发布代码，最后删旧列。代码和破坏性迁移放在同一次发布里，回滚时会读不懂新数据。

## 自测

1. 为什么容器里要收到 `SIGTERM`？这样才会走 `server.close`，而不是被直接杀掉。
2. 存活检查里应该访问数据库吗？不应该。那是就绪检查的事。
3. 内存上限和 `--max-old-space-size` 怎样配合？给 V8 一个更低的堆上限，把其余 rss 留给堆外内存。
