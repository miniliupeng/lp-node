# B03 文件进阶：替换要落在同一个目录

对应示例：[`examples/node-tutorial/B/03-atomic-write.mjs`](../../../examples/node-tutorial/B/03-atomic-write.mjs)

## 直接写目标文件的问题

`writeFile(target, data)` 如果中途进程崩溃，目标文件可能只写了一半。读配置的一方会看到半个 JSON。

## 同目录换名

示例的做法：

1. 在目标文件同一目录写临时文件 `.config.json.<pid>.tmp`
2. `rename` 临时文件到目标名
3. 再读出来，内容是完整的 `{"ok":true}\n`

在同一文件系统上，`rename` 替换已有名字是一个目录项操作。读者要么看到旧文件，要么看到新文件，不会看到半截内容。

这依赖两个条件：

- 临时文件和目标在同一文件系统。跨设备的 `rename` 会得到 `EXDEV`，那时需要复制，复制过程又有半截问题。
- 需要断电后仍在磁盘上时，还要在 `rename` 之前对文件描述符 `fsync`，并对目录 `fsync`。示例没有做 `fsync`，它证明的是“读者看不到半截 write”，不是“断电不丢”。

并发写同一个目标时，每个写者使用自己的临时名（示例把 `pid` 放进名字）。两个 `rename` 仍会分出先后，最后一个赢。需要“只有版本号匹配才替换”时，这套做法不够，要在应用层加版本或锁。

## 权限与符号链接

写临时文件时使用期望的权限。`rename` 到一个符号链接上时，平台行为要单独确认。上传目录这种不可信位置，先按 [A08](../A/08-process-path.md) 把路径收进根目录。

## 监听文件变化

`fs.watch` 的事件在不同系统上粒度不同，可能重复，也可能在编辑器“写临时文件再替换”时只看到一次 `rename`。配置热加载要能容忍重复事件，并在回调里重新读完整文件。教程不把 `fs.watch` 当成精确的变更日志。

## 自测

1. 为什么临时文件要和目标在同一目录？为了落在同一文件系统，`rename` 才能做替换。
2. 这套做法保证断电不丢吗？不保证。那需要 `fsync`。
3. 两个进程同时替换，结果是什么？后完成的 `rename` 留下它的内容。
