# B05 TCP：字节流没有消息边界

对应示例：[`examples/node-tutorial/B/05-tcp-frame.mjs`](../../../examples/node-tutorial/B/05-tcp-frame.mjs)

## TCP 给什么

`net.createServer` / `net.connect` 提供双工字节流。一次 `write` 可能被拆成多次 `'data'`，多次 `write` 也可能粘在同一次 `'data'` 里。应用层要自己定义帧。

HTTP 是一种帧格式：头和正文以空行分开，正文长度由 `Content-Length` 或分块编码决定。你自己的 TCP 协议也需要类似的规则。

## 长度前缀

示例使用 4 字节大端无符号长度，后面跟 UTF-8 正文。

```text
[uint32 length][length bytes payload]
```

解析器保留未完成的尾部。不到 4 字节，或正文还没收齐，就等下一次 `'data'`。收齐一帧就交给回调，并把剩余字节留在缓冲里。

长度上限设为 1 MiB。没有上限时，对端可以声明一个巨大的长度，让你一直分配内存。

示例把 `one` 和 `two` 两帧拼成一次 `write`。服务器拆出两帧，分别回 `echo:one` 和 `echo:two`。客户端用同一个解析器收两帧。这就覆盖了“粘在一起”的情况。

## 半包

如果断言只在“一次 write 一次 data”的本机回环上通过，仍然要保留缓冲。把解析器写成“没有完整帧就 return”，半包才会在下一次数据到来时接上。示例的 `createParser` 就是这样。

## UDP 只在这里点一句

`node:dgram` 提供数据报。每个消息有边界，但可能丢、重复、乱序，大小也有上限。需要可靠传输时用 TCP，或在 UDP 之上使用已经设计好的协议。教程示例不实现 UDP。

## 自测

1. 为什么不能按一次 `write` 等于一条消息来写协议？TCP 不保留这个边界。
2. 长度前缀为什么要有最大值？防止按对端声明的数字分配内存。
3. 解析器为什么要保存尾部？一帧可能分多次到达。
