# Worker

示例：`examples/C/09-worker.mjs`

`worker_threads` 的每个 Worker 是独立的 V8 isolate。普通对象不能共享。通信用 `postMessage`，数据按结构化克隆算法复制。

示例主线程把 1 到 10 发给 Worker，Worker 求和 55 再发回来。

`SharedArrayBuffer` 是真正共享的内存。一边 `Atomics.store`，另一边 `Atomics.load`。示例断言读到 42。没有 `Atomics` 时，编译器可以缓存读取，你可能永远看不到对方的写入。

Worker 脚本必须是真实文件。`node -e` 的 eval 路径不能当 Worker 入口，会 `MODULE_NOT_FOUND`。示例用 `import.meta.url` 判断自己是主线程还是 Worker，同一文件两边用。

Worker 适合 CPU 密集计算。I/O 密集的 HTTP 服务通常先用多进程，见[多进程](./10-多进程.md)。创建 Worker 有启动成本，用池，而不是每个请求新建一个。


## 是什么

每个 Worker 是独立的 V8 隔离实例。普通对象经 `postMessage` 按结构化克隆复制。`SharedArrayBuffer` 才是共享内存，读写用 `Atomics`。没有 `Atomics`，编译器可以缓存读取，你可能永远看不到对方的写入。

示例把 1 到 10 交给 Worker，求和得到 55。另一段用 `Atomics.store` / `load` 断言读到 42。Worker 脚本必须是真实文件。`node -e` 的路径会 `MODULE_NOT_FOUND`。示例用 `import.meta.url` 区分主线程和 Worker，同一个文件两边用。

## 池，而不是每请求一个

创建 Worker 要启动隔离实例、解析模块。HTTP 请求路径上新建 Worker 经常比计算本身还贵。CPU 密集任务用固定大小的池。I/O 服务先用多进程，见[多进程](./10-多进程.md)。

Worker 里的未捕获异常默认杀掉这个 Worker，不自动杀掉主进程。要监听 `error` 和 `exit`，决定是否补充新的 Worker。

## 本章问答

### 1. postMessage 是共享还是复制？

**考点：** 结构化克隆。

**回答：** 默认复制。函数、原型方法会丢掉。`SharedArrayBuffer` 放进消息里传递的是引用，两边看见同一块内存。普通 `ArrayBuffer` 可以被转移，转移后发送端不能再使用它。

### 2. 为什么示例不能用 eval 路径当 Worker？

**考点：** 模块加载要有文件 URL。

**回答：** Worker 按文件 URL 加载脚本。`node -e` 没有这样的文件，会 `MODULE_NOT_FOUND`。测试和示例都写成真实文件。

### 3. Atomics 解决什么？

**考点：** 可见性。

**回答：** 共享内存上的普通读写可以被重排或缓存在寄存器里。`Atomics.store` 和 `Atomics.load` 提供顺序和可见性。只为了传一个数字，优先 `postMessage`，不要先上共享内存。

## 事故复盘

每个请求 `new Worker`。CPU 没满，延迟却高，时间花在启动隔离实例上。用固定大小的池。

把函数当消息发给 Worker，对面是 `undefined`。结构化克隆不带函数。传数据，让 Worker 文件里自己有函数。

共享内存不用 `Atomics`，读者一直看到旧值。需要共享再用 `SharedArrayBuffer`，否则 `postMessage` 更不容易错。
