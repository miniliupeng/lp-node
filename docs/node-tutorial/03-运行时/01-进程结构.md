# 进程里的三层

示例打印版本：`examples/A/01-hello.mjs`。

一次 `node app.mjs` 启动一个操作系统进程。进程里：

- **V8** 解析并执行 JavaScript，分配堆上的对象。
- **libuv** 跑事件循环，并把部分阻塞操作交给线程池。
- **Node 绑定** 把 `fs`、`net`、`http`、`crypto` 接到这两层。OpenSSL 提供哈希和 TLS。

主线程同一时刻只执行一段 JavaScript。`await` 让出的是调用栈，不是 CPU 线程。CPU 密集的同步循环会挡住这个进程里的所有请求。

线程池默认 4。`UV_THREADPOOL_SIZE` 必须在进程启动时设置，[线程池与 DNS](./05-线程池与DNS.md)的实验证明异步 `readFile` 和 `pbkdf2` 在 22.23.4 上共用它。

`worker_threads` 是同一进程里的另一个 V8 isolate，堆不共享，除非显式使用 `SharedArrayBuffer`。`cluster` 是多个进程，见[工作线程](./09-工作线程.md)和[多进程](./10-多进程.md)。


## 是什么

一次 `node app.mjs` 是一个操作系统进程。里面有 V8、libuv、以及把 JavaScript 调用变成系统调用的绑定。OpenSSL 提供哈希和 TLS。undici 提供全局 `fetch`。

## 三条扩容路线不要混

| 路线 | 共享什么 | 适合 |
| --- | --- | --- |
| 异步 I/O | 一条 JavaScript 线程 | 很多连接，每段代码很短 |
| `worker_threads` | 进程，不共享堆。`SharedArrayBuffer` 除外 | CPU 密集计算 |
| `cluster` 或多副本 | 什么 JavaScript 堆都不共享 | 把 I/O 服务铺到多个核 |

线程池默认 4。`UV_THREADPOOL_SIZE` 在进程启动时读取。[线程池与 DNS](./05-线程池与DNS.md) 的实验证明异步 `readFile` 和 `pbkdf2` 在 22.23.4 上共用它。

## 本章问答

### 1. 网络 I/O 和文件 I/O 在这个版本上一样吗？

**考点：** epoll 和线程池。

**回答：** 不一样。TCP 的就绪由多路复用通知，不为每个连接开线程。22.23.4 上异步 `readFile` 仍走线程池。不要根据别的版本的博客说文件 I/O 已经默认改成 io_uring。

### 2. Worker 和 cluster 选哪个做 HTTP？

**考点：** 共享和故障边界。

**回答：** 先用多进程。一个进程崩溃不影响其他进程。Worker 适合把计算从主线程挪走。每个请求新建 Worker 的启动成本不划算，用池。

### 3. 改 process.env.UV_THREADPOOL_SIZE 为什么对当前进程无效？

**考点：** 读取时机。

**回答：** 库在启动时读这个变量。要比较不同大小，就 `spawn` 一个带新环境的子进程。示例就是这样做的。

## 事故复盘

把图像压缩的同步循环放进 HTTP 处理函数。连接数不高，事件循环延迟仍然到了秒级。网络多路复用不会帮你跑这段 JavaScript。CPU 密集的部分放进 Worker 池，I/O 服务用多进程。

在运行中的进程里设置 `UV_THREADPOOL_SIZE`，`pbkdf2` 仍只有 4 个并发。变量要在启动时就存在。示例用子进程证明了这一点。

把「Node 是单线程」写成运维文档，排障时没人去看 libuv 的工作线程。JavaScript 是一条线程，文件和慢哈希不是。
