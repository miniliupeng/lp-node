# 定时器与 I/O 顺序

示例：`examples/C/03-io-order.mjs`、`examples/B/08-timers.mjs`。

在 `fs.readFile` 的回调里依次注册 nextTick、微任务、`setImmediate`、`setTimeout(fn, 0)`，22.23.4 上的顺序是：

```text
nextTick → microtask → immediate → timeout
```

原因：

- 当前回调结束后先排空 nextTick，再排空微任务。
- `setImmediate` 在随后的 check 阶段运行。
- `setTimeout(fn, 0)` 被钳成至少 1ms，进入之后某一轮的 timers。

主模块顶层没有「当前 I/O 回调」，poll 是否立刻返回取决于有没有到期定时器，所以顶层的 `setTimeout(0)` 与 `setImmediate` 谁先谁后不稳定。示例不断言这个顺序。

`setTimeout` 的延迟大于 2147483647 也会被钳成 1。不要用一个超大数字表示「很久以后」。

长时间的同步循环会推迟所有这些回调。先用 `performance.now` 量循环本身，再谈事件循环。


## 是什么

在 `fs.readFile` 的回调里依次注册 nextTick、微任务、`setImmediate`、`setTimeout(fn, 0)`，22.23.4 上的顺序是：

```text
nextTick → microtask → immediate → timeout
```

## 为什么这个顺序稳定

回调结束时先排空 nextTick 和微任务。`setImmediate` 排在随后的 check。`setTimeout(fn, 0)` 被钳成至少 1ms，进入之后的 timers。主模块没有「当前 I/O 回调」，所以那一对顺序不稳定。

延迟大于 2147483647 也会被钳成 1。不要用一个超大数字表示「很久以后」，它会变成大约 1ms。32 位有符号整数的上限是这个钳制的来源。

长时间的同步循环会推迟所有这些回调。先用 `performance.now` 量循环本身，再谈事件循环。

## 本章问答

### 1. I/O 回调里谁先，setImmediate 还是 setTimeout(0)？

**考点：** 阶段顺序。

**回答：** `setImmediate` 先。回调在 poll 里，下一段是 check，timers 要等下一轮。示例 `examples/C/03-io-order.mjs` 把 nextTick 和微任务也排在它们前面。

### 2. 超大的延迟会怎样？

**考点：** 钳制。

**回答：** 大于 2147483647 的延迟被当成 1。想表示很长的时间，就用一个你真的打算等待的数值，或者用外部调度，而不是 `setTimeout(fn, 2**40)`。

### 3. 怎样证明是同步代码堵住了循环？

**考点：** 测量点。

**回答：** 在循环前后打 `performance.now`。循环本身花了几十毫秒，则定时器不可能在这之前跑。`monitorEventLoopDelay` 的单位是纳秒，见[性能测量](./11-性能测量.md)。

## 事故复盘

在 `readFile` 回调里用 `setTimeout(fn, 0)` 希望比 `setImmediate` 更早做清理。实际是 immediate 先跑，清理还没做，下一段代码已经读到旧状态。I/O 回调里的顺序是 nextTick、微任务、immediate、timeout。

用 `setTimeout(fn, 9999999999)` 表示「几乎不要跑」。延迟超过 2147483647 会被钳成 1，回调几乎马上发生。长时间等待用一个真实的毫秒数，或外部调度。
