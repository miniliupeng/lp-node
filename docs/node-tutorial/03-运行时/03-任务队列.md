# nextTick 与微任务

两个队列：

- **nextTick 队列**：`process.nextTick`
- **微任务队列**：`queueMicrotask`、`Promise.then`、`await` 的恢复

一次 JavaScript 调用结束后，Node 先把 nextTick 队列排空，包括回调里新加的 nextTick，再进入一个微任务检查点。微任务里新加的 nextTick，要等这次检查点结束后再排。

`examples/C/01-event-loop-cjs.cjs` 在 CJS 顶层断言：

```text
nt1 → nt2 → mt1 → p1 → mt-from-nt → mt2 → nt-from-mt
```

含义：

1. 先跑已排队的 nextTick。`nt1` 里又排了 `nt2`，所以 `nt2` 紧跟其后。
2. 然后才是原来的微任务 `mt1` 和 `p1`。`mt1` 里排的 `mt2` 仍在这次检查点里。
3. `mt1` 里排的 `nt-from-mt` 留到检查点之后。
4. `nt1` 里排的 `mt-from-nt` 属于这次微任务检查点，排在 `nt-from-mt` 之前。

ESM 入口的求值本身发生在微任务检查点里。同一段注册在 `examples/C/02-event-loop-mjs.mjs` 得到：

```text
mt1 → p1 → mt2 → nt1 → nt-from-mt → nt2 → mt-from-nt
```

已经在 Promise 回调里时，新微任务先于新的 nextTick。`examples/C/04-async-order.cjs` 的内层断言：

```text
microtask → promise → nextTick
```

外层在 CJS 顶层是：

```text
async-start → nextTick → after-await → promise → microtask
```

`async-start` 是同步部分。`await null` 把恢复排成微任务，所以它落在 nextTick 之后、和其他微任务一起。

面试时先说明入口是 CJS 还是 ESM，再讲顺序。背一条「永远 nextTick 优先」会在 ESM 入口翻车。


## 是什么

两套队列：`process.nextTick` 的队列，以及 V8 的微任务队列（`queueMicrotask`、`Promise.then`、`await` 的恢复）。当前调用栈结束后，若这次调用不是发生在微任务检查点里，Node 先把 nextTick 排空，包括回调里新加的 nextTick，再进入微任务检查点。微任务里新加的 nextTick 留到这次检查点之后。

## 三组已经断言的顺序

CJS 顶层，`examples/C/01-event-loop-cjs.cjs`：

```text
nt1 → nt2 → mt1 → p1 → mt-from-nt → mt2 → nt-from-mt
```

ESM 入口的求值发生在微任务检查点里，`examples/C/02-event-loop-mjs.mjs`：

```text
mt1 → p1 → mt2 → nt1 → nt-from-mt → nt2 → mt-from-nt
```

已经在 Promise 回调里时，新微任务先于新的 nextTick。`examples/C/04-async-order.cjs` 的内层是 `microtask → promise → nextTick`。外层 CJS 是 `async-start → nextTick → after-await → promise → microtask`。

所以「nextTick 绝对先于 Promise」只在当前栈不是微任务检查点时成立。旧答案把这句话说成永远成立，在 ESM 入口会错。

## 饥饿

无限 `nextTick` 时，timers 和 I/O 都排不上。`examples/C/17-nexttick-starve.cjs` 在 400 次之内断言 `timeout` 和 `immediate` 还没发生，队列清空之后它们才会出现。

## 本章问答

### 1. 为什么同一段注册在 CJS 和 ESM 里顺序不同？

**考点：** 入口本身在不在微任务检查点里。

**回答：** CJS 顶层先排空 nextTick。ESM 模块求值发生在微任务检查点里，所以先看到微任务。讲顺序之前先说入口是哪一种。两组顺序都有示例断言，不要凭记忆互换。

### 2. await 的恢复算什么？

**考点：** 微任务。

**回答：** `await` 把函数的后半段排成微任务。在 CJS 顶层，它落在已经登记的 nextTick 之后、和其他微任务一起。同步部分 `async-start` 仍在调用 `async` 函数的那条栈上立刻执行。

### 3. 递归 nextTick 会怎样？

**考点：** 饥饿。

**回答：** 队列不空，事件循环不进入后续阶段。连接不再被读取，定时器不触发。只在当前栈结束前要做很少的清理时用 `nextTick`。循环处理数据用 `setImmediate`，让 I/O 有机会插入。

## 事故复盘

库的初始化在 ESM 入口里登记 `nextTick` 和 Promise，作者按 CJS 的顺序写断言，升级到原生 ESM 后测试失败。ESM 求值在微任务检查点里，微任务会先跑。两组顺序都在 `examples/C/01-event-loop-cjs.cjs` 和 `examples/C/02-event-loop-mjs.mjs`。

递归 `nextTick` 用来「尽快处理队列」。网络不再读取，进程却不退出。`examples/C/17-nexttick-starve.cjs` 在 400 次之内定时器还没发生。循环让出用 `setImmediate`。
