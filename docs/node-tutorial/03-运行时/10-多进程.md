# cluster

示例：`examples/C/10-cluster.mjs`

`cluster` 把同一份脚本跑成多个进程。主进程 `fork`，Worker 进程执行请求处理。它们不共享 JavaScript 堆。

默认调度在非 Windows 上是 `SCHED_RR`。示例只起一个 Worker，用 `listen(0)` 让系统选端口，Worker 通过 IPC 把端口发给主进程。

主进程用 `http.get` 并且 `agent: false`，避免 keep-alive 把套接字留着，导致进程不退出。响应正文匹配 `/^pid:\d+$/`。

收到结果后向 Worker 发 `SIGTERM`。Worker 里 `server.close()` 再退出。主进程用 `cluster.once('exit')` 等待。

多个 Worker 不能共用一个进程内的 `Map` 当会话或限流计数。要共享就用外部存储，或者接受「每进程一份」的语义。

`listen` 同一个端口时，主进程负责分发连接。不要在 Worker 里再假设自己看到了全部流量。


## 是什么

`cluster` 把同一份脚本跑成多个进程。它们不共享 JavaScript 堆。非 Windows 上默认调度是 `SCHED_RR`：主进程接受连接，再把句柄交给下一个 Worker。Windows 上默认把监听句柄交给操作系统去抢。可以用 `cluster.schedulingPolicy` 查看当前策略，不要在没运行的平台上背死一个演示结果。

## 为什么多个 Worker 能 listen 同一个端口

在轮询策略下，真正对操作系统 `bind` / `listen` 的是主进程。Worker 里的 `listen` 通过 IPC 向主进程要连接，而不是各自再绑一次，所以不会 `EADDRINUSE`。主进程把已经接受的连接句柄交给一个 Worker。Worker 看不到全部流量，进程内的 `Map` 也看不到其他 Worker 的计数。

示例只起一个 Worker，用 `listen(0)`，通过 IPC 把端口发回来。主进程用 `http.get` 且 `agent: false`，避免 keep-alive 把套接字留着导致不退出。收到正文后发 `SIGTERM`，Worker 里 `server.close()` 再退出。

零停机重载不是 `cluster` 的一个函数。外部监督进程可以先 `fork` 新 Worker，等它开始监听，再让旧 Worker 停止接新连接并处理完在途请求。一次只替换一个，其余继续服务。这是滚动替换，不是「同时杀掉再启动」。

## 本章问答

### 1. 为什么不会 EADDRINUSE？

**考点：** 谁在 listen。

**回答：** 轮询模式下主进程持有监听套接字，Worker 收到的是已经接受的连接。不是四个进程各自成功 `bind` 了同一个端口。`SCHED_NONE` 则是共享监听句柄，由操作系统分发，负载可能不均。

### 2. 限流计数放在 Worker 的全局变量里会怎样？

**考点：** 堆不共享。

**回答：** 每个进程各算各的。限额变成进程数乘以单进程限额。全局限额要放进所有进程都能原子更新的存储。会话 id 同理。

### 3. 平滑重载的顺序是什么？

**考点：** 先有新的，再停旧的。

**回答：** 启动新 Worker，确认它已经能接受连接，再让旧 Worker `close` 并处理完在途请求，然后退出。不要一次向所有 Worker 发 `SIGKILL`。在途请求的收尾见[优雅退出](../04-工程与系统设计/10-优雅退出.md)。

## 事故复盘

四个 Worker 各自在内存里做令牌桶。限流阈值被放大到大约四倍，攻击流量没有被挡住。全局限额要共享存储。

发布时一次 `kill` 所有 Worker。在途请求全部断开。正确的滚动是先起新的，确认在监听，再让旧的 `close`。

`http.get` 默认 keep-alive，示例进程不退出，被当成死锁。探测请求关掉 agent，见 `examples/C/10-cluster.mjs`。
