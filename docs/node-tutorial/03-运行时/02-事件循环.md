# 事件循环阶段

libuv 按阶段转圈。和日常代码有关的是：

1. **timers**：到期的 `setTimeout` / `setInterval`
2. **pending callbacks**：部分系统回调
3. **idle / prepare**：内部使用
4. **poll**：取出已完成的 I/O
5. **check**：`setImmediate`
6. **close callbacks**：例如 socket 的 `close`

`process.nextTick` 不是一个阶段。`queueMicrotask` 和 Promise 回调也不是。它们在每个 JavaScript 回调结束之后被排空，见[任务队列](./03-任务队列.md)。

poll 阶段如果没有到期定时器，可以阻塞着等 I/O。有到期定时器时，它会回来让 timers 跑。因此「`setTimeout(fn, 0)` 一定比 `setImmediate` 早」在主模块里不成立。[定时器](../02-进阶/08-定时器.md)只断言两者都发生。

I/O 回调内部再注册时，顺序稳定。`examples/C/03-io-order.mjs` 在 `readFile` 回调里得到：

```text
nextTick → microtask → immediate → timeout
```

`setImmediate` 属于当前这轮的 check。`setTimeout(fn, 0)` 要等下一轮 timers，并且延迟至少被钳成 1ms。

不要用 `MessageChannel` 冒充微任务。`examples/C/16-message-channel.cjs` 在 CJS 顶层得到：

```text
nextTick → microtask → message → immediate
```


## 是什么

libuv 按阶段转圈。和日常代码有关的是 timers、pending callbacks、idle/prepare、poll、check、close callbacks。每个阶段取出一批回调执行。`nextTick` 和 Promise 微任务不是阶段。它们在 JavaScript 回调结束之后被排空，不是「只在两个阶段之间排一次」这么简单。见[任务队列](./03-任务队列.md)。

## poll 和定时器的关系

poll 如果没有到期定时器，可以阻塞着等 I/O。有到期定时器时，它会回来让 timers 跑。因此主模块里 `setTimeout(fn, 0)` 和 `setImmediate` 谁先谁后不稳定。[定时器](../02-进阶/08-定时器.md) 只断言两者都发生。

I/O 回调内部再注册时顺序稳定。`examples/C/03-io-order.mjs` 得到 nextTick、微任务、immediate、timeout。此时代码跑在 poll 的回调里，随后是 check，所以 `setImmediate` 先于下一轮的 timers。

`MessageChannel` 的 `message` 不是微任务，也不是官方阶段名。CJS 顶层示例的顺序是 nextTick、微任务、message、immediate。

## 本章问答

### 1. 六个阶段里哪些你要能按顺序说出来？

**考点：** 名字和职责，而不是背源码行号。

**回答：** timers 跑到期的 `setTimeout` / `setInterval`。pending callbacks 处理一部分系统回调。idle/prepare 给内部用。poll 取 I/O。check 跑 `setImmediate`。close callbacks 跑关闭回调。`nextTick` 不在这张表里。

### 2. 为什么主模块里的 setTimeout(0) 和 setImmediate 不能当面试标准答案？

**考点：** 区分稳定和不稳定。

**回答：** 延迟被钳成至少 1ms。循环启动时这 1ms 到了没有，取决于机器。22.23.4 上我们不断言这个顺序。I/O 回调里的顺序有断言，可以讲。

### 3. 微任务是在阶段之间才清空吗？

**考点：** 清空的时机。

**回答：** 每个 JavaScript 回调结束后都会排空 nextTick 和微任务，包括 poll 里的每一个 I/O 回调。不是等到六个阶段都走完才清空一次。递归 `nextTick` 会让阶段永远排不上，见 `examples/C/17-nexttick-starve.cjs`。

## 事故复盘

面试答案写「nextTick 是 timers 和 poll 之间的一个阶段」。它不是阶段。回调结束后就会排空，所以 poll 里的每一个 I/O 回调之后都会跑。把它画成六个阶段之一，会推错 `setImmediate` 和定时器的位置。

用一次主模块打印证明 `setTimeout(0)` 先于 `setImmediate`。换一台机器顺序反了，测试被改成重试三次。主模块的顺序不要当契约。I/O 回调里的顺序有示例。

`MessageChannel` 被当成微任务。CJS 顶层的顺序是 nextTick、微任务、message、immediate。message 排在微任务之后。
