# 测量

示例：`examples/C/11-perf.mjs`

先量，再改。`console.time` 足够做一次对比。更细的间隔用 `performance.mark` 和 `performance.measure`。

`monitorEventLoopDelay({ resolution: 20 })` 采样事件循环延迟。`enable()` 之后做一段 40ms 的同步阻塞，再 `disable()`。返回值的单位是纳秒。示例只断言最大值大于 20ms，不断言精确值。

延迟变大，说明主线程有一段时间没回到事件循环。常见原因是同步 JSON、同步压缩、大循环、`readFileSync`。

`process.memoryUsage().arrayBuffers` 用来看 Buffer。`process.cpuUsage()` 看用户态和内核态 CPU。

一次请求的火焰图比猜「是不是事件循环满了」有用。压测时固定 Node 版本、池大小和负载，否则两次数字不能比。


## 是什么

先量再改。`performance.now` 和 `performance.measure` 量一段 JavaScript 的耗时，单位毫秒，时钟单调。`monitorEventLoopDelay` 采样事件循环被耽搁了多久，返回值的单位是纳秒。示例阻塞约 40ms，只断言最大值大于 20ms，不断言精确值。

## 怎样不把纳秒读成毫秒

`mean`、`max`、`min` 都是纳秒。除以 `1e6` 才是毫秒。读错单位会得出「延迟只有零点零几毫秒」或「延迟有几秒」这种相反的结论。

延迟变大，说明主线程有一段时间没回到事件循环。常见原因是同步 JSON、同步压缩、大循环、`readFileSync`。数据库慢是另一段时间：从发出查询到回调开始。两段分开量，否则你会去调事件循环，而慢的是 SQL。

`process.cpuUsage()` 看用户态和内核态。`process.memoryUsage()` 看堆和 Buffer。压测时固定 Node 版本、线程池大小、并发和机器，否则两次数字不能比。

## 本章问答

### 1. 事件循环延迟的单位是什么？

**考点：** 纳秒。

**回答：** `monitorEventLoopDelay` 的直方图是纳秒。和 `performance.now` 的毫秒差 100 万倍。写报表前先换算，并在列名里写上单位。

### 2. 延迟高就一定是库的问题吗？

**考点：** 主线程上的同步区间。

**回答：** 先在可疑代码前后打点。若这一段本身就占了几十毫秒，瓶颈就是这段同步代码。若打点很短而延迟仍高，再看别的请求是不是在同一进程里做重活。

### 3. 为什么示例不断言精确的 40ms？

**考点：** 测量的噪声。

**回答：** 调度、GC 和机器负载会让一次采样偏离。断言用下界，把打印出来的值当观察，不当成契约。

## 事故复盘

把 `monitorEventLoopDelay` 的 `max` 直接当毫秒画图。单位是纳秒，图上的「几十毫秒」被画成几千万。除以 `1e6`，列名写单位。

一次压测改了机器和 Node 版本，结论是优化有效。两次数字不能比。固定版本、池大小和并发再比。

数据库慢和主线程慢被合成一个总计时，团队去改 SQL，其实慢在同步 JSON。两段分开量。
