# 大厂高频面试题精讲 (03-auth-cookie-session-jwt)

---

### Q1: Cookie/Session 与 JWT（JSON Web Token）方案有何本质区别？在实际大厂架构中如何选型？

#### 🎯 面试官考点
- 有状态（Stateful）vs 无状态（Stateless）认证架构权衡、分布式 Session 扩展性瓶颈。

#### 💡 满分回答模板
| 维度 | Cookie + Session (有状态) | JWT (无状态) |
| :--- | :--- | :--- |
| **存储位置** | 服务端维护状态（Redis / 内存）；客户端只存随机 `sessionId` | 服务端**不存任何状态**；所有身份数据加密签名后存在客户端 |
| **分布式扩容** | 依赖共享 Redis 集群；如果 Redis 宕机，全站用户登录态丢失 | **天然适合跨机器分布式扩容**，任何节点凭本地密钥即可独立验签 |
| **注销与吊销** | **极度容易**（服务端从 Redis 中直接删掉 key，会话立即失效） | **极难**（一旦签发，在到期前不可逆，除非引入黑名单） |
| **网络开销** | 很小（Cookie 只有一个短小的 sessionId 字符串，几十字节） | 较大（随着 Payload 字段增多，每次 HTTP 请求头都需要带几百字节上千字节） |

- **选型策略**：
  - **中后台管理系统、强安全金融应用**：优先选 **Cookie/Session**，能够随时强制踢出违规用户；
  - **移动端 App、对外 OpenAPI、跨地域/跨机房微服务网关**：优先选 **JWT**，零集中式查询压力。

### Q2: 现代 Web 安全中，Cookie 的 `HttpOnly`、`Secure` 与 `SameSite` 属性分别防范了什么攻击？

#### 🎯 面试官考点
- Web 安全防御三剑客：XSS 攻击、中间人嗅探与 CSRF 跨站伪造请求防护。

#### 💡 满分回答模板
1. **`HttpOnly`（核心防范 XSS 盗取凭据）**：
   - 阻止客户端 JavaScript 通过 `document.cookie` 读取该 Cookie。
   - 即使网页被黑客注入了恶意 XSS 脚本，黑客也无法通过 JS 偷走用户的登录凭证，大幅降低 XSS 危害。
2. **`Secure`（核心防范网络中间人明文窃听）**：
   - 规定该 Cookie 只能在 **HTTPS 加密连接** 下被浏览器发送。如果用户在不安全的 HTTP 明文环境下访问，浏览器拒绝携带该 Cookie，防止局域网抓包嗅探。
3. **`SameSite`（核心防范 CSRF 跨站请求伪造攻击）**：
   - **`Strict`**：最严格模式。任何跨站请求（哪怕用户在第三方网站点击了一个正常的超链接跳转过来）都不会携带该 Cookie。
   - **`Lax`（现代浏览器默认）**：宽松模式。常规跨站 POST 表单、图片/脚本加载不携带 Cookie；只有当用户通过导航跳转（如点击 `<a>` 链接）发起顶层 GET 请求时才会携带。
   - **`None`**：任何跨站请求均携带，必须同时配置 `Secure` 属性。

### Q3: JWT 是无状态的，如果用户密码被修改、账号被封禁，或者点击了“退出登录”，服务端该如何优雅地主动让 JWT 失效？双 Token（Access Token + Refresh Token）机制是如何工作的？

#### 🎯 面试官考点
- 无状态 JWT 的注销软肋解决方案与工业级双 Token 刷新架构。

#### 💡 满分回答模板
1. **主动失效的三种工业级方案**：
   - **方案 A：Redis 短期黑名单机制（Blacklist）**：
     - 用户退出登录时，将当前 JWT 的唯一标识 `jti` 存入 Redis，TTL 设置为该 Token 的剩余过期时间。网关验签时若发现 Token 在黑名单中则拒绝。由于只需存储极少量的退出的 Token，内存占用微乎其微。
   - **方案 B：Token 附带用户版本号（Version / LastPasswordResetAt）**：
     - 在 JWT 的 Payload 中塞入 `passwordVersion: 1`。当用户修改密码时，数据库中该用户的版本号递增为 2。网关解析出版本号不匹配立即拒接。
2. **双 Token（Dual-Token）标准工业实践**：
   - **Access Token（访问令牌）**：
     - **超短生命周期**（如 5~15 分钟），无状态，网关高频纯本地验签，即使被窃取也很快过期。
   - **Refresh Token（刷新令牌）**：
     - **超长生命周期**（如 7~30 天），**保存在服务端数据库/Redis**。仅在 Access Token 过期时，由客户端在后台默默向 Auth 服务发起无感刷新请求；
   - **优势**：当需要强制封禁用户时，服务端只需将该用户的 Refresh Token 从数据库删除，15 分钟内该用户的 Access Token 到期后将无法再续期，自动下线，既兼顾了微服务无状态的高性能，又具备了完全可控的主动吊销能力。
