# 大厂高频面试题精讲 (02-sqlite-embedded-database)

---

### Q1: 为什么现代 Node.js 官方要在 22.5+ 原生内置 `node:sqlite`？它解决了历史第三方模块的什么痛点？

#### 🎯 面试官考点
- 原生运行时演进、C++ 原生扩展编译（`node-gyp`）痛点与轻量嵌入式存储趋势。

#### 💡 满分回答模板
1. **彻底摆脱 `node-gyp` 本地编译梦魇**：
   - 过去使用 `better-sqlite3` 或 `sqlite3` 时，必须依赖 Node-API（N-API）和操作系统的 Python / C++ 编译工具链（`node-gyp`）。在 Docker 精简镜像（如 Alpine）或受限 CI/CD 流水线中，经常因为缺少编译头文件或跨平台交叉编译导致 `npm install` 严重报错甚至卡死几十分钟。
   - 原生内置后，由 Node.js 官方静态编译打包进运行时，**零外部依赖、零本地编译、开箱即用**。
2. **轻量化与边缘端标准化**：
   - 在 Serverless、CLI 工具、边缘开发与本地离线桌面端应用中，开发者不再需要为了存几条元数据而专门配置一套臃肿的网络数据库（如 MySQL/PostgreSQL）。

### Q2: 什么是 SQL 注入漏洞？预编译语句（Prepared Statements）在数据库底层是如何彻底杜绝 SQL 注入的？

#### 🎯 面试官考点
- 数据库词法/语法解析流程（Lexical/Grammar Parsing）与参数占位符的底层隔离机制。

#### 💡 满分回答模板
1. **SQL 注入本质：指令与数据混淆**：
   - 如果使用字符串拼接：`"SELECT * FROM users WHERE name = '" + input + "'"`。
   - 当输入为 `admin' --` 时，拼接出来的字符串变成了两个逻辑部分：前面的查询条件被单引号闭合，后面的 `--` 把数据库后续的密码验证逻辑直接注释掉了。数据库 SQL 词法分析器误将用户的输入当成了**控制指令语法**执行。
2. **预编译语句的彻底杜绝原理**：
   - **第一步（先编译框架）**：调用 `db.prepare("SELECT * FROM users WHERE name = ?")` 时，数据库引擎会先将这条纯净的 SQL 模板解析生成**抽象语法树（AST）与执行计划**并固定缓存起来。此时语法结构已经定型，占位符 `?` 只是一个纯粹的变量插槽。
   - **第二步（后填入数据）**：后续调用 `.run(input)` 传递用户数据时，数据库直接把输入内容作为**原始纯文本字面量（Literal Value）**送入执行引擎，**绝对不会再去重新走一遍词法解析**。哪怕输入包含十个单引号或 `DROP TABLE`，在数据库眼里也仅仅是一串包含特殊字符的名字而已，彻底从物理根源上消灭了 SQL 注入。

### Q3: 什么是 SQLite 的 WAL（Write-Ahead Logging）模式？相比传统回滚日志模式有什么并发优势？

#### 🎯 面试官考点
- 存储引擎并发控制（Concurrency Control）与读写互斥锁优化。

#### 💡 满分回答模板
1. **传统回滚日志（Rollback Journal）的痛点**：
   - 默认模式下，SQLite 采用库级排他锁。**写操作会完全阻塞所有的读操作，读操作也会阻塞写操作**，并发吞吐量极低。
2. **WAL 预写日志模式的颠覆性优势**：
   - 开启命令：`db.exec("PRAGMA journal_mode = WAL;")`；
   - **读写完全不互斥（并发飞跃）**：
     - **写操作**：新写入的数据不会直接改写主数据库文件，而是顺序追加到一个独立的 `-wal` 预写日志文件中；
     - **读操作**：读者直接去读取主数据库文件，并结合 WAL 日志合并最新视图；
     - 结果：**读者不会阻塞写者，写者也绝对不会阻塞读者（Readers do not block writers, and writers do not block readers）**，大幅提升高并发读取场景下的整体吞吐量与响应速度。
