# 大厂高频面试题精讲 (03-async-local-storage)

---

### Q1: 为什么在 Node.js 中绝对不能用全局变量（如 `global.currentUser`）保存当前请求的用户信息？`AsyncLocalStorage` 解决的核心痛点是什么？

#### 🎯 面试官考点
- 单线程事件循环中的并发交错执行模型与上下文隔离。

#### 💡 满分回答模板
1. **全局变量必发“串单污染”**：
   - Node.js 的主执行线程是单线程的，所有并发的 HTTP 请求共享同一个进程全局命名空间。
   - 当请求 A 进入，把 `global.currentUser = 'Alice'`；随后请求 A 发起了异步数据库查询（此时让出主线程）；
   - 紧接着请求 B 进入，把 `global.currentUser = 'Bob'`；
   - 此时请求 A 的数据库查询完成，继续执行后续入库或下单逻辑，此时它从 `global.currentUser` 取出的居然变成了 `'Bob'`！导致极其严重的业务资损与数据串单事故。
2. **`AsyncLocalStorage` 解决的核心痛点**：
   - 它在异步调用链之间自动传播存储引用。即便两个并发请求的代码在单线程中穿插交错执行，也能保证**在每个回调/Promise 恢复执行时精准绑定属于它自己的上下文**，彻底实现“无感跨函数隐式传递 TraceId / User 上下文”。

### Q2: `AsyncLocalStorage` 与 Java 中的 `ThreadLocal` 有何异同？

#### 🎯 面试官考点
- 跨语言并发模型认知：多线程并发 vs 单线程异步非阻塞事件驱动。

#### 💡 满分回答模板
1. **本质目的相同**：
   - 两者都是为了在不显式修改每个函数入参签名的前提下，跨越深层调用栈隐式共享与请求绑定的上下文数据。
2. **底层实现机制截然不同**：
   - **Java `ThreadLocal`**：绑定在**物理/虚拟线程（Thread）**实例上。因为传统 Java 一个请求由一个固定线程从头到尾处理，所以只要以 Thread 为 Key 就能天然隔离。
   - **Node.js `AsyncLocalStorage`**：绑定在**异步资源句柄（Async Resource）**的生命周期上。因为 Node.js 所有请求共用同一个物理线程，它依赖底层 `async_hooks` 机制，在每次创建异步操作（如创建 Timer、发起 Socket I/O、新建 Promise）时，自动将上下文引用传递给下游新生成的异步资源。

### Q3: `AsyncLocalStorage` 是否有性能损耗？在大厂超高并发场景下如何做选型权衡？

#### 🎯 面试官考点
- 底层实现演进与企业级生产性能压测认知。

#### 💡 满分回答模板
1. **性能演进**：
   - 在早期的 Node 8~12 时代，依赖纯 JavaScript 实现的 `async_hooks` 开销非常大（可能导致吞吐量下降 20%~50%）；
   - 在 Node.js 14+ 之后，官方在 V8 引擎与 C++ 层重构了 `AsyncLocalStorage` 的底层底层传播机制（利用 V8 PromiseHook C++ 原生接口），现代基准压测显示其性能损耗通常**小于 1%~3%**，日常生产服务完全可以放心作为标配使用。
2. **使用避坑指南**：
   - **不要存储过大对象**：存储数据应尽量保持轻量（如只放 `traceId`, `tenantId`, `userId` 等元信息），避免持有大对象引用阻止垃圾回收（GC）。
   - **慎用非标准异步封装**：如果对接某些陈旧的、直接跳过 Node.js 标准事件循环调度（如极个别 C++ 原生扩展），可能导致上下文丢失，需用 `als.bind()` 手动桥接。
