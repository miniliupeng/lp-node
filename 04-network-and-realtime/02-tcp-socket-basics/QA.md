# 大厂高频面试题精讲 (04-tcp-socket-basics)

---

### Q1: 什么是 TCP 的“粘包”与“半包”？底层为什么会出现这种现象？UDP 也会粘包吗？

#### 🎯 面试官考点
- 传输层协议本质差异：面向字节流（Stream）vs 面向数据报（Datagram）。

#### 💡 满分回答模板
1. **本质原因（TCP 没有“包”的概念）**：
   - TCP 协议在设计之初是一个**面向连续字节流（Stream of Bytes）**的协议。在 TCP 内核眼里，只有源源不断的字节序列，根本不知道开发者发送的一句话、一个 JSON 对象的边界在哪里。
   - **粘包（Packet Sticking）**：发送端连续调用两次 `write`，操作系统内核为了提高网络利用率（例如 Nagle 算法），将多个小数据包合并进同一个 TCP 报文段发送；或者接收端网卡接收较慢，多个包堆积在接收缓冲区被一次性读出。
   - **半包（Packet Splitting）**：发送端发送了一个超过 MTU（最大传输单元，通常 1500 字节）或接收窗口限制的大包，TCP 协议栈会在内核层强制将其切片为多个小分段。
2. **UDP 不会发生粘包**：
   - UDP 是**面向数据报文（Datagram-oriented）**的协议。UDP 报文头中包含显式的长度字段，发送端调用一次 `sendto`，接收端调用一次 `recvfrom` 必定精准收到对应的一个完整报文，具有天然的边界隔离。

### Q2: 工业界解决 TCP 粘包与半包的常见方案有哪些？各有什么优缺点？

#### 🎯 面试官考点
- 应用层自定义协议设计能力（RPC 协议头设计）。

#### 💡 满分回答模板
解决粘包半包的唯一手段：**在应用层协议中人为定义消息边界**。业界通用 3 大方案：
1. **固定长度定界（Fixed Length）**：
   - 规定每个包固定 128 字节，不足用空格或 0 补齐。
   - *优缺点*：实现极简单；但对于短文本浪费带宽，对于超长文本无法承载，极不灵活。
2. **特殊分隔符定界（Delimiter-based）**：
   - 例如使用 `\r\n` 或自定义特殊字符（如 Redis 协议 RESP、HTTP 请求头以 `\r\n\r\n` 结尾）。
   - *优缺点*：文本协议可读性极好；但如果业务内容本身恰好包含了分隔符，就必须引入复杂的转义逻辑，CPU 逐字节扫描开销大。
3. **固定消息头 + 动态消息体（Length-Field / TLV 模式，最主流！）**：
   - 消息头固定占用 4 个字节，存放后续消息体 Body 的真实字节长度；接收端先读取 4 字节拿到长度 $L$，再精确从流中截取 $L$ 字节作为完整 Body。
   - *优缺点*：无任何内容转义限制，天然支持二进制与 JSON，是 gRPC、Dubbo、各类游戏私有协议的标准工业实践。

### Q3: 什么是 Nagle 算法？为什么在实时通信或低延迟 RPC 中必须设置 `socket.setNoDelay(true)`？

#### 🎯 面试官考点
- 网络吞吐量（Throughput）与交互延迟（Latency）的权衡调优。

#### 💡 满分回答模板
1. **Nagle 算法的初衷**：
   - 为了防止网络上充斥着只有 1 个字节载荷、却带着 40 字节 TCP/IP 报头的“微型小包”（Silly Window Syndrome）。
   - Nagle 算法规定：如果连接上有已发送但尚未收到 ACK 确认的数据，发送端后续的小数据包会被**强制暂存挂起**，直到积累够一个 MSS（最大报文段长度）或者收到了对端的 ACK 确认，才合并一次性发送。
2. **现代场景下的冲突**：
   - 现代 TCP 接收端普遍开启了“延时确认（Delayed ACK）”机制（等待 40ms~200ms 再回 ACK）。
   - 当 Nagle 算法遇到 Delayed ACK 时，双方会陷入长达数百毫秒的互相死等，导致网络交互延迟陡增！
3. **`socket.setNoDelay(true)` 的作用**：
   - 该 API 会在操作系统底层设置 `TCP_NODELAY` 标志位，**强制立即关闭 Nagle 算法**。
   - 一旦调用 `socket.write()`，数据包立即原样向网络发射，绝不等待合并，极大降低了按键响应、RPC 调用和在线竞技游戏的网络端到端延迟。
