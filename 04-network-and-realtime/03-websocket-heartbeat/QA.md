# 大厂高频面试题精讲 (04-websocket-heartbeat)

---

### Q1: 请简述 WebSocket 的协议升级（Handshake）过程。客户端发送了哪些特殊请求头？服务端如何计算响应签名？

#### 🎯 面试官考点
- WebSocket 协议 RFC 6455 握手规范与魔术字符串（Magic String）哈希校验。

#### 💡 满分回答模板
1. **客户端发起 HTTP GET 请求并携带升级标头**：
   - `Connection: Upgrade`
   - `Upgrade: websocket`
   - `Sec-WebSocket-Version: 13`
   - `Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==`（客户端随机生成的 16 字节 Base64 字符串，用于防止代理缓存误判）。
2. **服务端握手确认与计算签名**：
   - 服务端提取客户端的 `Sec-WebSocket-Key`，将其与一个固定的全球标准 GUID（魔术字符串：`258EAFA5-E914-47DA-95CA-C5AB0DC85B11`）进行字符串拼接；
   - 对拼接后的字符串执行 **SHA-1 哈希加密**，然后转为 **Base64 编码**，填入响应头 `Sec-WebSocket-Accept`；
   - 返回 HTTP 状态码 **`101 Switching Protocols`**。客户端验证该响应头与自己预期计算的一致后，握手正式完成，后续通信脱离 HTTP，转换为双工 WebSocket 二进制数据帧。

### Q2: 既然操作系统的 TCP 协议自带了 Keep-Alive 机制，为什么在 WebSocket 和长连接应用层中我们仍然必须手写心跳保活（Ping/Pong）？

#### 🎯 面试官考点
- 传输层 Keep-Alive 的局限性、中间设备超时回收与应用层死锁检测。

#### 💡 满分回答模板
1. **TCP Keep-Alive 的致命迟钝性**：
   - 操作系统原生的 TCP Keep-Alive 默认探测时间非常漫长（Linux 默认空闲 **7200 秒（2 小时）** 才发第一次探测包，之后每隔 75 秒重试一次）。对于实时聊天、在线协作等业务来说，用户掉线 2 小时后系统才发现是完全不可接受的！
2. **中间网络设备（NAT / 防火墙）的空闲超时截断**：
   - 运营商基站、家庭路由器和云负载均衡器内部都维护着 NAT 映射表。为了节省内存，绝大多数中间网关在连接**空闲超过 60 秒~120 秒**时就会单方面默默将该映射表项抹除。此时双方以为连接还在，但实际数据流已被网关阻断。
3. **应用层死锁与假死（Ghost Connection）无法被 TCP 层感知**：
   - 如果服务端的 Node.js 进程发生事件循环死锁或高 CPU 阻塞，此时操作系统的内核网络协议栈仍然是正常的，它还会继续自动回复底层的 TCP ACK 包！
   - 只有在**应用层执行 Ping/Pong**，必须由 Node.js 主线程处理逻辑并回传数据，才能 100% 验证当前 Node.js 应用进程是否真正健康具备响应能力。

### Q3: 在设计长连接断线自动重连时，为什么要使用“带随机抖动的指数退避算法（Exponential Backoff with Jitter）”？如果直接固定每 1 秒重连会有什么灾难？

#### 🎯 面试官考点
- 惊群效应（Thundering Herd Problem）、服务雪崩防范与客户端重试退避哲学。

#### 💡 满分回答模板
1. **固定重连间隔引发的“惊群雪崩”**：
   - 假设服务器发生临时闪断或重启，100 万在线用户同时断开连接。
   - 如果客户端全部固定每 1 秒重连一次，那么这 100 万客户端将在第 1 秒、第 2 秒整齐划一地同时向网关发起握手请求！瞬间形成峰值 QPS 高达数十万的流量海啸，直接把刚刚重启拉起的服务端再次打死，陷入恶性循环的持续雪崩。
2. **带随机抖动的指数退避（Jittered Backoff）的妙用**：
   - **指数退避**：重试间隔随着失败次数呈指数级拉长（例如 1s, 2s, 4s, 8s, 16s... 达到最大上限）。给服务端的故障自愈恢复争取宝贵的喘息时间。
   - **随机抖动 (Jitter)**：在计算出的延时上叠加一段随机值（例如 $\text{Delay} = \text{Exponential} + \text{random}(0, 500\text{ms})$）。
   - **打散流量尖峰**：将 100 万客户端原本集中在同一瞬间的重连请求，均匀分散到不同的时间切片上，将尖锐的“脉冲尖峰”抹平成平缓的“低矮长流”，从而保护服务端顺利完成流量接管。
