# 大厂高频面试题精讲 (01-node-runtime-and-pnpm)

---

### Q1: 都说 Node.js 是单线程的，那它为什么能处理高并发？它真的只有一个线程吗？

#### 🎯 面试官考点
- 考察对 Node.js 架构（V8 + libuv + 线程池）的本质理解。
- 区分“用户 JS 代码执行单线程”与“底层系统 I/O 线程池”的边界。

#### 💡 满分回答模板
1. **概念纠偏**：Node.js 的“单线程”指的是 **JavaScript 代码的主执行环境和事件循环（Event Loop）运行在单线程上**，而不是整个 Node.js 进程只有一个线程。
2. **底层架构解剖**：
   - **网络 I/O**：通过操作系统底层的非阻塞多路复用机制（Linux 的 `epoll`、macOS 的 `kqueue`、Windows 的 `IOCP`）实现，完全不需要额外的 OS 线程即可处理成千上万个并发网络连接。
   - **文件 I/O 与加密/压缩计算**：由底层 **libuv 维护的线程池**（默认 4 个线程，可通过 `UV_THREADPOOL_SIZE` 调优）在后台异步执行，执行完成后将回调推入事件循环。
3. **高并发优势**：避免了传统多线程服务器为每个连接分配独占栈内存（如 1MB~8MB）带来的内存暴涨与昂贵的 CPU 线程上下文切换，因而非常适合 **I/O 密集型**（高并发轻运算）场景。

### Q2: 相比传统 npm / yarn，pnpm 的底层核心原理是什么？什么是“幽灵依赖”？

#### 🎯 面试官考点
- 对现代前端工程化包管理工具机制的理解。
- 硬链接（Hard Link）、软链接（Symbolic Link）与内容寻址存储（CAS）。

#### 💡 满分回答模板
1. **硬链接与全局 CAS 存储**：
   - pnpm 在磁盘全局维护一个统一的存储目录（Store），同一版本依赖包只下载一次。
   - 项目内的 `node_modules` 里的文件是直接通过操作系统**硬链接**（Hard Link）指向全局 Store，不仅下载安装极速，而且多个项目复用同一依赖时几乎不占用额外磁盘。
2. **杜绝幽灵依赖（Phantom Dependencies）**：
   - **幽灵依赖定义**：npm/yarn v1 为了避免深层嵌套采用扁平化提升（Hoisting），导致子依赖被提升到根 `node_modules`。开发者在业务代码中可以偷偷 `import` 未在自身 `package.json` 声明的依赖。一旦上游依赖升级不再依赖该包，生产环境打包直接报错。
   - **pnpm 的解法**：pnpm 的根 `node_modules` **只包含** `package.json` 里显式声明的依赖软链接，所有真实物理包存放在 `.pnpm` 扁平目录内，严格隔离非显式依赖。

### Q3: CommonJS (CJS) 与 ECMAScript Modules (ESM) 的本质区别有哪些？

#### 🎯 面试官考点
- 模块加载时机（运行时动态 vs 编译期静态）。
- 值的输出方式（值拷贝 vs 动态只读引用）。
- 循环引用的处理与异步 top-level await 支持。

#### 💡 满分回答模板
| 维度 | CommonJS (`require`) | ECMAScript Modules (`import`) |
| :--- | :--- | :--- |
| **加载时机** | **运行时同步加载**（代码执行到才加载） | **编译期/解析期静态分析**（必须在模块顶层） |
| **导出机制** | **输出值的拷贝**（修改原变量不影响已导出的值） | **输出值的动态只读引用**（修改会实时映射） |
| **Top-Level Await** | 不支持（必须包裹在 async IIFE 中） | **原生支持顶层 await** |
| **Tree-Shaking** | 难以做静态 Dead Code 消除 | **天然支持编译期 Tree-Shaking** |
| **全局变量** | 自带 `__dirname`, `__filename`, `exports` | 无内置魔术变量，改用 `import.meta.url` 衍生 |
